# Technical Architecture (iOS, Android & Cloud Sync)

**Balashikshana** is architected as an **offline-first, cross-platform mobile game and study platform** for **iOS and Android** tablets and phones, backed by a containerized microservice API for multi-device progress synchronization, parent analytics, and over-the-air (OTA) curriculum bundle delivery.

## 2. Mobile Client Architecture (iOS & Android)

### 2.1 Cross-Platform Layer
- **Runtime:** React Native (Expo SDK 58, RN 0.88, React 19 — roadmap D1) with **React Native Skia**, **Reanimated 4**, and **Rive**.
  - **60/120 FPS Rendering:** Skia provides hardware-accelerated 2D canvas drawing for Bezier letter tracing (`trace-draw-studio`), particle effects, ten-frame physics blocks (`block-builder`), and fast-moving sprites (`bubble-pop-blitz`).
  - **Vector Animations:** Rive state machines power interactive characters and study manipulatives at `< 50 KB` per asset.
- **App Shell & Design System (M3, issue #43):** the shipped foundation every M3 screen builds on.
  - `apps/mobile/src/design/tokens.ts` — pure-data single source for color (semantic `light`/`dark`/`highContrast` themes + text-grade `statusInk`), spacing, radius, and the kid-scale type ramp; vitest-enforced invariants (>= 48pt touch targets, WCAG contrast floors per theme).
  - Primitives (`Button`, `PressableCard`, `ProgressBar`, `Badge`, `Sheet`) with the tactile 3D treatment and a global reduced-motion provider (`MotionProvider` honors the OS accessibility setting; zero-duration degradation, nothing load-bearing).
  - `expo-router` tree: launcher + the real onboarding flow (below) + the readiness-guarded real `journey` map (2.7) + placeholder `practice` / `gate` runners (their param contract is already fixed: `{ gradeId, unitId }`); no dead ends.
  - Quality gates: ESLint (flat, `eslint-config-expo`) + Prettier + strict `tsc` + vitest, wired into the single CI job.
- **Onboarding & Consent Chain (M3, issue #44):** the client that drives the M2 parent/consent/child API end to end (`src/onboarding/`).
  - A pure state machine (`state.ts`) with a resume planner: the step snapshot (one-row `expo-sqlite` table, secret-free) plus secure-store credentials plus a read-only server reconcile (consent status + children) decide the landing step after any interruption. Duplicate safety comes from in-flight markers persisted before the create-child POST — a kill mid-submission adopts the landed child or re-submits, never both.
  - Storage seams (`storage.ts` + `nativeStores.ts`): every credential (parent session, child-device, pending verification token, draft child PIN, install device id) routes exclusively through `expo-secure-store`; the SQLite snapshot is structurally incapable of carrying a secret, and the vitest suite enforces that on serialized snapshots.
  - Client consent doctrine: consent is captured before any child-data call, re-asserted server-side before child creation, and a 409 `policy-version-mismatch` always re-renders the new policy text before re-acceptance. A policy bump re-locks child surfaces (the journey guard consults consent status; offline it falls back to the last-known accepted version while the server remains the enforcement authority).
  - Parental gate: a reusable hold-to-confirm component (3-second continuous press, timer-based — animation settings cannot affect it) guarding onboarding and every parent/settings surface.
- **Audio & Phonetics Subsystem (M3 infrastructure, issue #45):**
  - `AudioCoordinator` facade (`apps/mobile/src/audio/`): the single entry point screens consume — `speak()` (TTS narration), `sfx()` (feedback sounds by id or `{moment, topicId}`), `haptic()` (feedback patterns), `stopSpeech()` (synchronous duck restore). Every platform capability is injected (speech / SFX / haptics / bundled-narration engines, settings store, clock, accessibility probes), so the entire policy surface is node-testable; the Expo adapters are isolated in one RN-only module (`nativeAudio.ts`) and the service bootstraps at the root layout via `getAudioService()`.
  - Grade-calibrated narration rate: rates derive from the curriculum registry (`docs/us-curriculum-registry.json`, per-topic `voiceNarration.speakingRateWpm`, uniform per grade — Pre-K 110, K 120, G1 130, G2 140, G3 150) and are clamped to 110–150 WPM before conversion to the platform multiplier. SSML narration input is adapted per platform (expo-speech has no SSML: tags stripped, prosody rates honored, break pauses preserved, and — since #59 — prosody pitch percents mapped to platform multipliers clamped to [0.5, 2.0], see 2.15).
  - Duck policy (`duckPolicy.ts`, pure count-based state machine): while any narration utterance speaks, SFX volume scales to 0.3; the multiplier restores only when every queued utterance reaches a terminal event (paired with its start), and cancel restores synchronously. Narration itself is never attenuated — it is the primary instructional channel for pre-readers — and narration defers while a screen reader is active so TTS never fights VoiceOver.
  - Manifest-driven SFX catalog: `assets/sounds/sounds-manifest.json` (repo root, 614 topics) references the 16 synthesized WAVs in `assets/sounds/`; the app's static asset registry is compile-time pinned to exactly those 16 stems and tests pin manifest == registry == disk in both directions. #46 (content packs) owns the on-device split and delivery of topic-to-soundpack data; until then the bundled manifest is the source.
  - Audio settings (sound effects / narration / haptics / music toggles) persist through the non-secret SQLite seam (`balashikshana_audio.db`, one-row, schema-version-guarded parse with per-field type guards) — never the secure store.
  - Pre-K fallback hook: when the device exposes no usable TTS voice, a bundled-narration seam is attempted before reporting `unsupported` (since #59 the seam is exercised across all five line kinds by test with an injected engine; no audio files ship — narration is synthesized, see 2.15).
  - Pre-packaged pure phoneme audio bank (`/m/`, `/s/`, `/a/`, `/sh/`, `/ch/`) for zero-latency phonics blending (planned with the bundled-audio milestone).
  - On-device Text-to-Speech (US English voice profile) for dynamic math word problem narration so pre-readers are tested on math reasoning rather than reading ability.

### 2.2 Procedural Question & Distractor Generator
Instead of static multiple-choice questions that children memorize after two attempts, each Skill Topic in [`us-curriculum-registry.json`](./us-curriculum-registry.json) is paired with a **Parameterized Question Generator**:
- Generates fresh numbers, visual configurations, and pedagogical distractors on every run.
- **Smart Distractor Generation:** Wrong choices are generated from common misconception models (e.g., for `52 - 18`, distractors include `46` [subtracted smaller from larger digit: `8 - 2`], `44` [forgot to borrow], and `36` [off-by-two computation error]).

### 2.3 Local-First Storage & Offline Play
- **On-Device SQLite Database:**
  - `learner_profiles`: Child UUID, avatar, current grade, motor baseline ($T_{\text{motor}}$).
  - `unit_progress`: `unit_id`, `status` (`LOCKED`, `STUDY_REQUIRED`, `GUIDED_PRACTICE`, `FLUENCY_READY`, `GATE_UNLOCKED`, `MASTERED`), `best_accuracy`, `best_median_speed_ms`, `attempts_count`.
  - `topic_mastery`: `unit_id`, `skill_topic_code`, `mastery_score` (0–100), `median_speed_ms`, `stability_days` ($S_m$), `last_reviewed_at`, `cpa_fading_stage`.
  - `assessment_telemetry`: Granular log of every gate attempt (`question_id`, `skill_topic_code`, `is_correct`, `raw_time_ms`, `cognitive_time_ms`, `fluency_grade_1_to_4`).
  - `spaced_repetition_queue`: `unit_id`, `skill_topic_code`, `retrievability_pct` ($R_m(t)$), `next_review_at`, `sleep_consolidation_key_state` (`SILVER_KEY` / `GOLD_KEY`).

### 2.4 Signed Content Pack Subsystem (M3, issue #46)
- **Compile-time (`tools/content-pipeline`):** the registry is compiled into one deterministic SQLite pack per grade — canonical JSON, fixed pragmas, single sorted transaction, `VACUUM`, no timestamps — then sealed with a detached Ed25519 signature and SHA-256 checksum in a manifest index. The same registry + key always rebuilds byte-identical artifacts, and the build refuses to publish any artifact that fails its own self-verification.
- **Serving:** the API serves the manifest index (`GET /api/content/packs`) and the signed artifacts (`GET /api/content/packs/:gradeId`, octet-stream, ETag = sha256) from the gitignored compiler output; it never verifies signatures (that is the device's job) but 503s on any index/artifact inconsistency.
- **On-device (`apps/mobile/src/content/`):** packs are verified before install — pinned public keys, size + checksum + signature, and a `pack_info` cross-check that the artifact describes exactly the grade/version the manifest promised — then published with one atomic rename and pruned under a 64 MB storage budget. Downgrades are refused; failed installs leave the previous pack active. Pack artifacts are opened read-only (`PRAGMA query_only`); content rows are never inserted on-device.
- **Trust model:** dev builds pin the committed dev key; production pins nothing until the release key is provisioned at M6 — an empty trust list fails closed (no pack installs) rather than trusting the dev key.
- **Forward schemas:** the pack lifecycle database (`balashikshana_content.db`) already carries the append-only `attempt_log` and `topic_progress` / `unit_progress` tables that the offline practice core (#47) and sync protocol (#48) populate.

### 2.5 Offline Practice Core (M3, issue #47)
- **Module layout (`apps/mobile/src/practice/`):** a pure, node-testable core — `PracticeSessionEngine` (topic / boss-gate / Gold-verification session orchestration), `AttemptRecorder` (append-only writes), `progressProjector` (attempts -> progress rows), `goldKey` (two-key state machine), `reviewQueue` (spaced-repetition due queue), `packShapes` (pack rows -> core-engine shapes, field-identical to the server's `mapQuestionRow`) — with exactly one RN adapter (`nativePractice.ts`: expo-sqlite lifecycle storage + a cached, `PRAGMA query_only` pack reader resolved through `pack_meta`) and a root-mounted `PracticeWarmup` fire-and-forget bootstrap. `packages/core-engine` is imported read-only via a `file:` workspace link and never modified (RN-side typings: `apps/mobile/src/types/core-engine.d.ts`); the Hermes export for both platforms is asserted to contain the engine.
- **Local D8 doctrine:** the attempt log is client-authoritative and append-only — INSERT is the only write, there is no UPDATE/DELETE path anywhere in the mobile tree (source-scan enforced), the AUTOINCREMENT `id` is the strictly monotonic sync cursor, and `synced` flips to 1 only after the #48 sync worker has durably applied the server's authoritative snapshot (the one documented UPDATE exception; the source-scan test pins that exact statement shape). Progress rows are a local projection of the log; responses are durable at submit time, projections run at session completion, so a crash mid-session loses no attempt data (the log is the recovery record; the server re-derives on sync).
- **Equivalence contract:** the projector mirrors `services/api`'s topic-complete and gate-evaluate derivations line-for-line — same engine calls, same rounding (`toFixed(1)` accuracy, `toFixed(2)` median), same crowns rule (3/2/1/0 at >= 95% and at-target speed / >= 85% / >= 80%), same GREATEST/LEAST upsert merges, sticky `MASTERED`, key COALESCE (an existing key is never nulled). Tests run identical streams (fixed + seeded-random) through both consumption paths and assert identical projections; a source tripwire pins the server's load-bearing derivation lines so server changes break the proof loudly. #48 resolved the #47 divergence list: (1) both sides now run the registry two-key machine — Silver on pass, Gold only via the frozen 14-hour window plus a 5-item verification with >= 4 correct (`services/api/derivations.mjs` is the single source the online handlers AND the sync reconciler reuse; the pre-#48 any-second-pass Gold promotion is retired); (2) topic-path cognitive time is computed with audio duration 0 exactly like the server's topic handler, while gate items use the engine's audio-aware rule; (3) the server now persists all three session types (migration 006; online rows get per-call session ids, synced rows carry device ids + client sequence numbers). Local gate outcomes and key states carry `provisional = 1` until a sync snapshot confirms or rolls them back.
- **Schema v2 (lifecycle DB):** purely additive `ALTER TABLE ... ADD COLUMN` statements plus the partial `idx_attempt_log_drain (student_id, id) WHERE synced = 0` — v1 statements are frozen, a v1 device upgrades in place with zero data movement, and the `user_version` runner never touches a database from a newer app version. `attempt_log` gains `unit_id`, `session_type` (`TOPIC_PRACTICE` / `GATE` / `GOLD_VERIFICATION`), `session_id`, `raw_time_sec`, `fluency_grade`, `misconception_tags_json`, `chosen_answer`; `topic_progress` gains the SR columns (`stability_days`, `next_review_at`, `last_review_at`, `fluency_grade`, `topic_code`, `provisional`); `unit_progress` gains the gate-projection columns (`best_median_speed_sec`, `stability_days`, `last_reviewed_at`, `cpa_stage`) plus `provisional`, `silver_awarded_at`, `gold_verified_at`.
- **Two-key sleep consolidation (registry `globalMasteryRules.twoKeySleepConsolidationGate`):** day-1 pass -> `SILVER_KEY` (provisional); Gold eligibility opens exactly 14 h after the FIRST Silver award (re-passing the gate never resets or re-arms the window); a 5-item verification with >= 4 correct upgrades to `GOLD_KEY` (provisional); transitions are forward-only — no local event revokes a held key (rollback is #48's server-authoritative concern).
- **Spaced repetition:** the review queue ranks due `topic_progress` rows by the engine's retrievability `R_m(t)` (most-forgotten first), and intervals are age-capped per grade from the pack's `sr_max_interval_days` (Pre-K 21 / K 30 / G1 45 / G2-G3 60 days) — the cap is enforced both inside `updateTopicMemoryStability` (via the per-grade policy) and again at scheduling time.
- **Question sourcing offline:** stored pack rows first (topic sessions: `difficulty ASC, question_id ASC LIMIT n`, mirroring the server's practice endpoint; gate sessions: the server's stratified round-robin across the unit's topics), with the engine's deterministic `generateTopicPracticeSet` padding any shortfall in a disjoint `-G` id space — identical items for identical seeds on both sides by construction.

### 2.6 Sync Protocol (M3, issue #48)
- **The loop (roadmap D8):** the mobile `SyncEngine` (`apps/mobile/src/sync/`) drains whole sessions from `attempt_log` in id order (front window via `idx_attempt_log_drain`, capped at the server's batch limit), uploads ONLY facts (raw time, audio, answers, tags, motor baseline — never client-computed derivations), adopts the server-authoritative snapshot (confirming or rolling back provisional local state, adopting server timestamps), and only then flips `synced`. A crash at any step loses nothing: rows replay, and the server dedupes by `(student, device, client_seq)`.
- **Whole-session contract with boundary deferral:** a batch carries only complete sessions. When the drain window is FULL, a cursor probe (`drainUnsyncedAfter` — rows strictly after the window's last id, never a re-read of the window) decides the trailing session's fate: it uploads whole only if the probe PROVES it ended (the unsynced remainder is exhausted, or a different session follows its last row) AND the extension fits the 200-attempt cap; otherwise the trailing session is DEFERRED and only the complete prefix uploads — the next pass's window starts at the deferred session's head, so a session that fits the cap always uploads whole and progress is guaranteed. A session larger than the cap is a loud fatal, never a silent split. Sessions the child is still answering (liveness probe) defer the same way. Uploadable groups are a strict prefix stopping at the first deferred group, so the synced-flag range flip (`markSyncedUpTo`) can never mark unuploaded rows. A configured batch size above the server cap is clamped client-side to 200 rather than wedging on a fatal 400.
- **Server reconciler (idempotent + convergent):** `POST /api/sync/attempts` (child-device tokens only — student binding and the idempotency device component both come from the token, never the body; consent-gated; archived children frozen out) inserts each attempt with `ON CONFLICT DO NOTHING` on the unique `(student, device, client_seq)` key, then — in the SAME transaction — replays every session that gained rows through the exact shared derivations the online handlers run (`services/api/derivations.mjs`). Defense-in-depth convergence: each replay runs over the UNION of the batch group and any previously persisted rows of the same `(student, session_id, session_type)` (the `idx_attempts_session` lookup), with exactly-once counting (a re-replayed session adds no count) and coin awards gated on the pass transition — so a client that violates the contract and splits a session across batches converges on the true session instead of double-counting it. Gold verification converges by construction (verdict over the union, forward-only transition). Documented residual: spaced-repetition stability takes exactly one growth step per session, at first arrival; a re-replay carries the stored stability and CPA stage through (the growth function is clamped, not invertible). `GET /api/sync/progress` returns the authoritative snapshot plus the content-version handshake without an upload.
- **Clock policy:** server timestamps are authoritative. Client `answered_at` in the past is accepted as-is (offline devices legitimately lag); a future timestamp beyond `SYNC_FUTURE_CLOCK_TOLERANCE_MS` (default 5 minutes) is clamped to server receive time and counted in `stats.clockSkewAdjusted`. The 14-hour Gold window is evaluated at the session's own adopted timestamp, so sync latency never extends eligibility.
- **Server schema (migration 006):** `student_question_attempts` gains `audio_duration_sec`, `session_id`, `device_id`, `client_seq` plus the partial unique index `uq_attempts_client_seq` (replayed batches insert nothing) and `idx_attempts_session` (the union-replay lookup); `student_unit_progress` gains `silver_awarded_at` / `gold_verified_at` (the two-key machine's persisted state). Attempts are immutable COPPA evidence: `device_id` deliberately has no foreign key into `devices()` so deleting a device row never cascades away its history.
- **Transport and battery doctrine:** the engine retries with exponential backoff + full jitter (fatal 400/401/403/404/413 never retry); offline runs pause without touching the transport. The controller fires only on app foregrounding, connectivity regain, and debounced post-practice nudges — no polling loops. Connectivity uses `@react-native-community/netinfo` (the supported reachability API for Expo; Expo SDK 58 ships no first-party connectivity module — decision documented in `nativeSync.ts`). `SyncBootstrap` mounts the controller at the root layout. Since #49 the bootstrap also wires the previously-dormant `clientPacks` handshake — the transport reports the device's active `pack_meta` versions on every upload/progress fetch, the server's `packsOutdated` answer reaches subscribers through `subscribeContentOutdated` (the journey's grade switcher marks stale grades), and the controller singleton is exported (`getSyncController()`) so screens share one in-flight-guarded instance. Endpoints, schemas, and the whole-session/clock contract are specified in `docs/openapi/baseline.yaml` (additive; oasdiff-gated).

### 2.7 Journey Map Screen (M3, issue #49)
- **Module layout (`apps/mobile/src/journey/`):** the same DI doctrine as practice/sync — a pure, node-testable derivation layer (`model.ts` states + garden math + deterministic winding layout, `store.ts` screen state machine, `loader.ts` pack+progress assembly, `art.ts` a11y art contract) with exactly one RN adapter (`nativeJourney.ts`: identity/snapshot, pack currency) plus the RN views (`JourneyScreen`, `JourneyPath`, `GardenHealth`, `GradeSwitcher`). Zero curriculum data in the module — everything renders from the installed #46 pack (query_only reader) and #47 progress rows; a vitest source-scan enforces both that and the no-native-imports purity of the pure layer.
- **State derivation:** all seven engine `UNIT_STATES` are computed, never stored — precedence LOCKED (any unmastered prerequisite, resolved inside the grade) > MASTERED / REMEDIATION_REQUIRED (unit row) > GATE_UNLOCKED (every topic complete at avg crowns >= 2, the projector's 85%-accuracy tier) > FLUENCY_READY (every topic complete) > GUIDED_PRACTICE > STUDY_REQUIRED; a held key is forward-only and outranks the ladder. Keys ride `unit_progress.key_state` with the provisional distinction (sync adoption clears it) and the 14-hour Gold-verification countdown; the FLUENCY_READY / GATE_UNLOCKED split is the journey's documented reading of the engine ladder (matrix-tested at the exact tier boundaries). Garden health is a pure aggregate (per-unit mastery fractions + gate-attempt health) — no hardcoded values.
- **Rendering:** one `react-native-svg` surface carries the track, nodes, glyphs, and key badges (path `d` and node centers precomputed by the deterministic `layoutWindingPath`, memoized on unit count + width only); node touch targets are thin >= 48pt Pressables over the surface. The single animated surface is the scroll-linked dash reveal (reanimated shared value, mounted only when the motion profile allows; reduced motion renders the static reveal). Added dependency: `react-native-svg` 15.16.0 — chosen over Skia (established OSS standard, lighter, sufficient for a static winding path; reanimated already covers motion).
- **Hydration and grade switching:** on mount the screen loads the local model first (offline-first), then kicks ONE sync run through the shared controller (`getSyncController()`) and re-derives with fresh post-snapshot data; the post-adoption reload targets the live grade via a ref. The store's `model-loaded` is guarded by the active grade, so a hydration racer can never render one grade's units under another grade's selection. Grade switching persists through the onboarding snapshot's `gradeId`; per-grade progress is preserved structurally (unit ids are globally unique). The switcher's pack currency — `installed` / `downloading` / `missing` / `stale` — runs missing/stale selections through the #46 `ensurePack` lifecycle (deduplicated per grade, downgrades refused; a stale flag keeps serving the installed last-good pack until the update resolves).
- **Accessibility:** every state encoding is shape+color redundant — a unique SVG glyph per state, Silver badge = circle, Gold = hexagon — and each node's spoken label carries state, key, provisional flag, countdown, topic census, and "you are here". Works unchanged in the `highContrast` theme (theme-independent glyphs; only fills resolve per theme).
- **Navigation seam (#50/#51):** node taps route to `/practice` and `/gate` with `{ gradeId, unitId }`; gate-adjacent states (FLUENCY_READY / GATE_UNLOCKED) go to `/gate`, everything actionable to `/practice`, LOCKED is disabled. The behavior comparison against the dev harness (D1 input) is documented in `docs/journey-harness-parity.md`.

### 2.8 Practice Session Runner (M3, issue #50)
- **Module layout (`apps/mobile/src/runner/`):** the same DI doctrine as practice/sync/journey — pure, node-testable modules (`interactionRegistry.ts` renderer registry + coverage check, `cpaStages.ts` stage ladder, `questionShapes.ts` row-to-widget adapters + render matrix, `requeue.ts` expanding-retrieval scheduler, `sessionStore.ts` UI state reducer) behind a pure-only barrel (`index.ts` exports nothing that transitively imports native modules); the RN layer is exactly the widget kit (`widgets/`, importable directly by the M4 game framework's practice-runner fallback, #52), one native-seams module (`runnerNative.ts`: engine singleton, audio coordinator, child-device identity), the 3-tap `MotorWarmup`, and the thin `PracticeRunnerScreen`. No network call exists in the runner tree — a full session runs offline from the installed #46 pack + the #47 engine.
- **Interaction inventory is data-derived, never hand-listed:** the seeded packs contain exactly three `interaction_type` values (multiple-choice 5,228 / tile-builder 712 / interactive-counter 200 of 6,140 rows), and `tests/runner-interaction-coverage.test.ts` re-derives that inventory the same way the #46 compiler seeds it (engine `generateTopicPracticeSet` over every registry topic), failing when any type has neither a renderer in `interactionRegistry.ts` nor an entry in `TRACKED_FALLBACK_TYPES` (empty at v1). The same test pins `docs/runner-interaction-coverage.md` — the human checklist — to exactly the derived inventory, so code, test, and doc cannot drift.
- **CPA scaffold ladder (engine-owned, mirrored not forked):** `stageForTopicProgress` reproduces the engine's `updateTopicMemoryStability` cpaStage thresholds line-for-line — stabilityDays < 1 `CONCRETE_INTERACTIVE`, >= 1 `PICTORIAL_STATIC`, >= 4 `PICTORIAL_GHOST_FLASH_1S` (a 1-second visual peek, then hidden), >= 10 `PURE_ABSTRACT_SYMBOLIC` — pinned against the engine across a stability sweep by `tests/runner-cpa.test.ts`. The stage ALWAYS comes from engine state (the topic's memory stability in the #47 progress projection), never from UI heuristics; a topic with no progress row starts concrete. `renderPlanFor` composes the interaction-type x stage matrix: the interactive manipulative is the answer surface only at the concrete stage; every later stage fades to the choice grid with progressively less scaffold (static picture -> 1-second flash -> none). Every seeded row carries a non-empty `choices` array (asserted), so the choice grid is the universal degraded-stage surface and no question can ever render unanswerable.
- **In-session expanding-retrieval re-queue:** the pure scheduler (`requeue.ts`) inserts three re-presentations of the SAME question row at Lag +2/+5/+10 intervening items when an ORIGINAL item is graded 1 (missed) or 2 (slow) — the constants are pinned equal to the engine's `intraSessionExpandingLags` by `tests/runner-requeue.test.ts`. A miss on an already re-queued item never extends the ladder (bounded, gentle sessions); a slot past the tail clamps to the tail — the +10 presentation becomes the session's "exit ticket" — and the queue is capped at 16 total items (re-queues past the cap are dropped; the cross-session spaced-repetition schedule still owns the topic). Re-queued presentations carry a SPACED REPLAY badge.
- **Widget kit v1 contracts (`src/runner/widgets/`):** `CounterFrame` (five-column tap-to-toggle counting frame — the manipulative IS the ten-frame), `TileBuilder` (tap-to-place tile bank into answer slots — tap, never fine-motor drag, for ages 3-9), `ChoiceGrid` (universal answer surface; selection is shape+color redundant — tinted fill AND solid border AND a check glyph), and `VisualScaffold` (the pictorial/ghost-flash visual row plus the manipulative-anchor chip derived from the row's `visual_aid` stem). All four are presentational (no session/engine/audio knowledge; the parent owns correctness), theme-aware across all three themes including highContrast, >= 48pt touch targets, animation-free (the ghost-flash window is content timing, not animation; press feedback honors the reduced-motion profile; nothing load-bearing animates). Seeded choice sets are test-pinned at <= 4 options, so the non-virtualized grid stays consciously bounded.
- **Deterministic presentation:** choice order is a Fisher-Yates shuffle seeded by a FNV-1a hash of the question id (xorshift32 stream) — no `Math.random` anywhere in the render path, so the same question presents the same order on every device; the seeded rows store the correct answer first, so presentation must never be unshuffled.

### 2.16 Placement Diagnostic (M4, issue #60 — roadmap E10, the placement half)

- **One pure engine module, seeded deterministic end to end:** `packages/core-engine/src/placement.mjs` — zero-dependency, no clocks, no `Math.random` (the rewards.mjs/hearts.mjs doctrine). Item selection advances a hand-rolled mulberry32 PRNG whose integer state threads explicitly through the probe state, so an identical seed yields an identical adaptive path on every device (`DEFAULT_PLACEMENT_SEED` 60; the server never needs the seed — outcome derivation is a function of responses, not the selection path). The numbers are POLICY CONSTANTS frozen in `PLACEMENT_RULES` like gate thresholds: `maxItems` 14 (the hard session bound; a strong child tops out at 2 strands x 7 depths), `maxSkipAheadUnits` 4, `provisionalBaseStabilityDays` 1.0, `dagCreditWeight` 0.4 (the engine default). Units arrive strand-keyed by registry subject with per-strand linear chains ordered `(sequenceOrder, unitId)`; the grade's first unit embeds the prior-grade entry link, so the depth-0 probe covers cross-grade prerequisites by construction.
- **Adaptive staircase probe, confirm-first frontier:** the probe walks each strand's chain from unit 1 — a correct depth-probe advances; a wrong one parks the strand in CONFIRMATION (one more item on the SAME unit); a second wrong answer confirms the frontier (the child starts there); a correct confirm treats the first miss as a slip and keeps advancing. Confirming strands resolve FIRST (a pending confirmation is the cheapest confidence gain), then the shallowest probing strand advances (round-robin keeps the probe representative of the grade, not deep on one subject), with a deterministic name tiebreak. Items are engine-generated (`generateProceduralQuestion` over a seeded topic pick — the SAME generator the practice API serves). The stopping rule: the session ends as soon as every strand has a confirmed frontier or hit its chain end, subject to the 14-item cap; units with no askable topics skip forward without blocking the probe.
- **SLIP-FORGIVENESS RULE (kid-optimistic, deliberate):** a once-wrong unit is still credited — even when its confirm item is cut off by the hard item cap. In the outcome derivation a unit probed with at least one item and at most one wrong counts as demonstrated (the "forgiven slip" walk in `derivePlacementOutcome`), in every path except a second wrong answer: the confirm item arrived and was correct (slip forgiven, the probe advanced), or the confirm item never arrived because the cap ended the session first — both credit the unit; only two wrongs on the same unit set the frontier there. The rationale is kid-optimistic by design: one-tap errors (a mis-tap, a rushed choice) must not pin a young child at the very start of a grade they largely know. The rule is bounded twice over — the 4-unit skip-ahead cap bounds how far a lucky or forgiving run can reach, and the credit it grants is PROVISIONAL and decays through the ordinary FSRS retrievability path if the child never actually practices there, so a forgiving outcome cannot lock in a wrong placement.
- **Order-independent start-point mapping (D8: both sides run it):** `derivePlacementOutcome` is a pure, order-independent function of per-unit response tallies over the strand chains — robust to attempt-stream batch splits and identical on client and server (the same union-replay convergence seam as every #48 session type). The frontier is the first confirmed-wrong (two or more wrongs) or unprobed (zero items) unit; everything before it is the credited prefix, capped by `maxSkipAheadUnits` on BOTH the credited prefix and the recommended start index (tested exactly at the boundary; a mid-grade re-run is a documented non-goal, and the cap bounds one run's blast radius). The recommended start is the earliest uncredited point across strands in journey order — so the start unit's prerequisite chain is fully credited or re-probed BY CONSTRUCTION (the structural `prerequisiteChainCredited: true`), and the module's outputs carry NO key vocabulary at all (`keysAwarded` is always empty): placement recommends and grants provisional credit; only a #51 Boss Gate ever awards a key, and no placement path marks a unit MASTERED or completes a topic.
- **Provisional credit is ordinary FSRS stability (no second memory system):** per CORRECT placement item the credited topic's stability grows through the engine's own `updateTopicMemoryStability` (growth factor 2.0, hard cap 4 days, base 1.0 day) — a single placement item can never out-stabilize a real practice pass — and wrong items grow nothing. The credited unit's largest topic delta feeds `propagateImplicitDagCredit` at weight 0.4, spreading implicit stability along prerequisite chains exactly like practice credit. Server-side, the reconciler's `PLACEMENT_TOPIC_CREDIT_SQL` upserts are stability-only: `completed`/`crowns`/`mastery_score` stay 0, no unit-status rows or key state are ever written, `next_review_at` re-arms, and stability takes `GREATEST` with the existing row. If the child never revisits the topic, the credit simply decays — placement evidence is a head start, not a verdict.
- **PLACEMENT session type + server recompute (D3/D8 parity):** `SESSION_TYPES` gains `PLACEMENT` (the additive #52 GAME precedent; the OpenAPI baseline's closed `AttemptInput` enum and the sync ledger schema carry the same value, older clients never send it). There is deliberately NO submit endpoint: the client uploads attempts (`POST /api/sync/attempts`, sessionType PLACEMENT) and `replayPlacementSession` recomputes the outcome from the session's FULL union of attempt rows through the same core-engine module the RN client ran at session close — identical stream, identical recommendation, pinned by a D8 agreement test plus split-batch convergence and idempotent-replay specs. The replay then (1) upserts the placement record via migration 009's `student_placement_records` — ONE row per `(student_id, grade_id)` (`uq_placement_student_grade`, CASCADE on student deletion, `down` additive), overwrite-in-place on re-entry — and (2) credits per-attempt XP over the NEW rows only (audio-aware, keyed idempotently like every session type — a correct placement answer is still a correct answer), with NO outcome XP and no coins: nothing was passed, there is nothing to celebrate numerically. GET `/api/placement/record?gradeId=` reads it under CHILD-DEVICE tokens only (parent and student-PIN sessions are 403 wrong-token-type), consent-gated, 404 when no placement ever synced for the grade. The record answers "what did placement find" — the family's accept-vs-gentle CHOICE is device-local journey state, deliberately not stored server-side.
- **Kid-safe mobile flow, thin over the pure modules:** the offer policy (`apps/mobile/src/placement/offer.ts`, pure) is per `(student, grade)` and asks exactly ONCE ever — `declined` (start at unit 1) or `completed` (the accepted start rides home) — and the offer NEVER blocks: the journey map stays fully interactive beneath the gentle card (`PlacementOfferCard` on `JourneyScreen`, shown on first grade entry and on a first switch into an un-decided grade). Resumability (#44): a kill anywhere before the decision write leaves no record, and the record's absence IS the resume state — the offer simply re-appears. `PlacementScreen` owns only timing capture, the #50 choice widgets, audio moments through the #45 coordinator (each question prompt spoken with the #59 `instruction` kind; a spoken app-copy celebration at the recommendation), and #58 mascot reactions. The recommendation screen ALWAYS shows both options — "start where recommended" (default) and the explicit gentler unit-1 start — and a decision-record write failure never strands the child (the route into practice happens regardless). Copy (`copy.ts`) frames the whole flow as a short exploration: no scores, no pass/fail, no anxiety vocabulary, mistakes neutral. The route (`app/placement`) is consent-guarded child-access (#52 game precedent); the decision record is device-local (content schema v8 `placement_records`, upsert-only). COPPA: unit ids and counts only — no free text, no PII anywhere in the flow.

## 3. Parent & Educator Analytics Portal

Delivered in M5 (issue #61, roadmap D4/D5): a separate lightweight web app at `apps/parent-portal` plus the `/api/portal/*` route family — deliberately NEVER linked from any child surface (no route, URL, or nav path from the Expo app or the :4200 web harness; D5 child-surface isolation). The portal is how the parent reads their children's learning telemetry and sets the controls the SERVER enforces on the child's device surfaces.

### 3.1 Stack decision — Vite SPA, right-sized (documented rationale)

The portal is a **Vite + React 19 + TypeScript (strict) SPA** with its own `package-lock.json` (the `apps/mobile` workspace precedent). Rationale vs the alternatives: a parent portal is a *thin authenticated client* of the existing Fastify API — every screen sits behind login, so there is no SSR, no SEO, and no public content for a framework like Next.js to render server-side; an SPA keeps the deployed surface to static files with zero server runtime of its own. No UI kit — hand-rolled components over `src/tokens.css` design tokens mirroring the repo's token philosophy. Charts are hand-rolled SVG (the quadrant is positioned dots, the weekly view is bars — zero chart dependencies), which also satisfies the issue's no-third-party-SDK acceptance (first-party code only; bundle audited clean). Dev origin is :4300 (`vite --port 4300 --strictPort`), added additively to the API's explicit CORS allowlist (env-driven; no wildcard, production guard intact).

### 3.2 Auth doctrine — parent tokens only, ownership structural

Every `/api/portal/*` route requires a **parent session token** through the #40 `requireParentAuth`: student PIN sessions and child-device tokens fail **403 wrong-token-type** (token-kind confusion tests extend the #40 middleware), anonymous callers are 401. Ownership is resolved SERVER-SIDE through `parent_children` — a child id in the path is only ever read after binding it to the caller's parent id, and another parent's child id returns the same uniform 404 as a nonexistent id (anti-enumeration; the repo's scoped-lookup convention). The SPA's token storage is a documented decision (`src/auth.ts`): **in-memory + a sessionStorage mirror** — survives an in-tab reload, never persists to disk across browser sessions, unreachable from other origins. localStorage was rejected (a disk-persistent 7-day credential; one XSS becomes week-long access) and cookies rejected (the API has no cookie/CSRF surface; no new auth semantics). On 401 the app attempts exactly ONE rotation via the #40 refresh endpoint, then returns to login — no silent retries.

### 3.3 Enforcement architecture — one source of truth, server-side

`services/api/enforcement.mjs` is the single source for reading a child's settings and deciding what they gate; the portal routes, the sync surfaces, and the question-serving routes all import it, so limits can never fork between surfaces.

- **Settings resolution:** through the CLAIMED binding only (`parent_children.status = 'claimed'`) — an unclaimed/archived child has no reachable row and platform defaults apply (no limit, nothing restricted, reminders off). The `LIMIT 1` read is deterministic because migration 005's partial unique index `uq_parent_children_claimed_student` makes exactly-one-claimant a database constraint. Migration 010's `portal_child_settings` carries the values (`daily_limit_minutes` NULL-or-5–480, `restricted_subjects` JSON array, `grade_ceiling` FK, the #57 reminder mirror).
- **Time limits (UTC day):** "over the limit" means the child's RECORDED active time for today's UTC day is at/over the cap — then `POST /api/sync/attempts` refuses any batch adding today-dated sessions (429 `time-limit-exceeded` + `Retry-After`), while pure backfill of earlier days always lands and the crossing session itself landed in full (attempts are never split; D8 append-only intact).
- **Content controls gate SERVING, never the ledger:** a restricted subject returns the question routes' same shape with ZERO questions (`contentRestricted`), the pack INDEX filters by grade ceiling for child callers, and above-ceiling pack artifacts are a 403 for child callers (byte-identical for anonymous callers). Controls never rewrite or delete recorded attempts.
- **Fail-closed grade vocabulary:** `GRADE_ORDER` is a frozen duplicate of the grades registry; if the registry ever grows a grade the list does not know, an unknown ceiling string RESTRICTS and an unknown unit gradeId is treated as ABOVE the ceiling — `indexOf`'s -1 can never widen access.
- **Honest signed-pack limit:** subject controls cannot be carved out of a SIGNED pack artifact (verification would break); they are enforced at question-serving instead. Pack artifacts are public content under the existing distribution doctrine — devices verify signatures; parental controls gate the child's experience, not curriculum secrecy.

### 3.4 Analytics — server-side aggregation, pure math

`services/api/portal-analytics.mjs` owns MEANING as pure, unit-tested functions (the `derivations.mjs` split: SQL fetches grouped rows from `student_question_attempts`; math never touches the db). Definitions are stable contracts:

- **Quadrant per skill topic** (architecture sec 3's chart, implemented): Y = accuracy %, split at the **80% platform pass line**; X = **median cognitive speed**, split at the topic's unit target speed (`units.gate_max_speed_sec` — the same fluency bar crowns use, so "fast" means at/under target). Top-right green fluent, top-left yellow accurate-but-slow, bottom-right orange rushing, bottom-left red needs-review. A topic with no usable target speed is still plotted but classified null (rendered gray — no invented split).
- **Weekly view:** Monday-anchored **ISO weeks in UTC** (the ledger stores clock-adjusted UTC ISO strings); "active time" is summed `cognitive_time_sec` — the ability-neutral measure (raw time systematically overstates time-on-task for younger/slower-motor kids). Weeks with no activity are **zero-filled data, never errors**; a topic counts as mastered in the week of its FIRST passing (>=80%) session.
- **parentSettings mirror:** `GET /api/sync/progress` carries an advisory `parentSettings` block (time limits incl. `exceeded`, content controls, notification defaults) so an offline-first device can gate locally BEFORE burning an upload — advisory only; the server-side refusals in 3.3 are the enforcement. The #57 reminder stays DEVICE-LOCAL per D5: the portal row is the parent-owned default; a device that wants it consumes the advisory block, and the device never uploads reminder state.

The US standards crosswalk (per-topic Common Core/NGSS codes) is carried by the curriculum registry and surfaced through the curriculum API/docs; the portal does not re-render it (M5 scope — see roadmap).

### 3.5 Data rights — export, deletion, retention, audit (issue #62, roadmap E11)

The COPPA data-rights surface under the same `/api/portal/*` doctrine (parent tokens only, the SAME exported `requireOwnedChild` ownership guard, uniform scoped-404): `GET /api/portal/children/{studentId}/export`, `DELETE /api/portal/children/{studentId}`, the append-only `deletion_audit` ledger (migration 011), and the retention sweep (`services/api/retention.mjs`). The portal exposes both as a per-child "Data and privacy" pane.

- **Export — one JSON document, parity by construction:** every child-data class in one attachment (profile, binding, child-bound consent records, effective portal settings, the full attempt ledger, topic/unit progress, student + device session lifetimes, gamification — XP events, badges, state —, session outcomes, placement records) plus an `analytics` block computed through the SAME exported helpers as the live quadrant/weekly endpoints (`quadrantPointsForChild` / `weeklySeriesForChild` in `portal.mjs`), so export numbers equal portal numbers by construction, verified by deep-equality tests. **Credential hygiene is column-level**: `pin_hash`, the student session token, and device `token_hash` are never selected; tests additionally scan the serialized document for every secret kind. Memory is bounded by one child's rows (all queries `student_id`-scoped, assembled and stringified once — a streaming writer would buy nothing at this scale and forfeit the shared aggregation path).
- **Deletion — password re-auth + one transaction, ordered and explicit:** the bearer token proves the session, the account PASSWORD proves the holder (verified against the stored scrypt hash — the login primitive, no new crypto; 12–128 bounds mirror signup; wrong password 401 `re-auth-required`; a dedicated per-IP bucket, the login-bucket doctrine for a password surface). One transaction: `SELECT ... FOR UPDATE` on the students row is both the concurrency mutex and an existence RE-CHECK (the ownership guard runs outside the transaction — a concurrent winner deleting the child in the window yields the uniform 404, never a phantom zero-count audit row), then explicit ordered deletes — attempts -> topic progress -> unit progress -> student/device sessions -> XP events -> badges -> gamification state -> session outcomes -> placement records -> portal settings -> the binding -> the child profile row (the schema's CASCADEs remain the belt-and-braces backstop) — the consent linkage severance, and the `deletion_audit` INSERT, all committing atomically. `devices` rows survive (parent-owned hardware registrations, not child data); a repeat request is the uniform scoped-404 (the binding is gone — the surface is idempotent). **Synchronous, no grace window** — a deliberate decision: COPPA does not mandate a cancellation period, the ACs demand a single-transaction cascade, and the friction ladder (token + password + hold-to-confirm + rate bucket) is proportionate; the audit ledger is the post-hoc accountability record. A grace window remains a future product option, not a compliance gap.
- **COPPA consent posture — keep the evidence, delete the child, the ledger carries the linkage:** verifiable parental consent records are RETAINED past a deletion request (FTC COPPA record-keeping expects the operator to be able to demonstrate consent for a retention period even after the child's data is deleted at the parent's direction); every child-specific row — including the PII-bearing students row (nickname, username, avatar, age) — is deleted. `consent_records.student_id` stays ON DELETE RESTRICT (migration 002's doctrine: nothing can CASCADE evidence away), so the sanctioned transaction itself severs the linkage (`student_id` -> NULL), counted in the audit row. The opaque child id thus survives in exactly one place — `deletion_audit` — which is the "audit linkage" the acceptance criteria allow.
- **Audit ledger — append-only at the storage layer:** `deletion_audit` (migration 011) has plain-text ids and NO foreign keys BY DESIGN (the ledger must outlive every row it describes, including a future parent-account deletion) and a BEFORE UPDATE OR DELETE trigger that raises — the same evidence-protection doctrine as the consent RESTRICT, one layer down. One production write site exists: the INSERT inside the deletion transaction. No API route reads or mutates it.
- **Retention sweep — idempotent TTL purges, scheduler honest about its limits:** `runRetentionSweep` purges rows whose `expires_at` has passed in the four TTL-bearing tables (`student_sessions`, `parent_sessions`, `child_device_sessions`, `parent_tokens`) with single-statement DELETEs — re-running reaches the identical end state (second pass deletes zero), concurrent API traffic only races the same per-row predicate, and exact-boundary rows (expires_at == now) purge on the `<=`. "Orphaned rows past retention" need no sweep of their own: every child-data table cascades from students, so orphans are structurally impossible. Scheduling is a boot pass + unref'd interval (`RETENTION_SWEEP_INTERVAL_MS`, default 6h, 0 disables; the sweep function is exported for scripts/tests with an injectable clock). The sweep NEVER touches consent_records, deletion_audit, or any attempt/progress row — evidence has no TTL; the one sanctioned attempt rewrite is the audited deletion itself. Logging is counts-only (no PII; the ledger is the record for deletion events, and expiry purges are not child-data deletions).
- **Portal pane — destructive action behind two independent gates:** the "Data and privacy" card offers the JSON download (blob download with the attachment naming mirrored client-side) and the deletion flow: plain-language consequence copy (what is deleted; what is retained and why), the account password, and a press-and-hold button (3s; keyboard Space/Enter equivalent) so no single tap can fire the irreversible call. Every gesture-interruption path cancels the hold — pointerup, pointerleave, pointercancel (touch scroll takeover fires it with NO pointerup), the long-press context menu, keyup, blur — and `touch-action: none` keeps scroll from claiming the gesture at all; only the primary pointer can start it (a reviewer-audit fix, mutation-proven by tests).

### 3.6 Weekly parent email summaries — mailer seam, scheduler, sent-ledger (issue #63, roadmap E11)

One email per eligible parent summarizing each linked child's completed week — the only outbound-mail surface, built on a transport seam so the server never depends on a mail provider to boot, test, or run.

- **Mailer seam — one interface, three transports:** `services/api/mailer.mjs` defines `send({ from, to, subject, text, html }) -> { ok, messageId?, error? }`. Transports RESOLVE, never reject — a failed send is `ok: false` and the digest batch isolates it with a plain result check. `createCaptureTransport()` records sends in memory (dev tooling and EVERY test — zero network I/O); `createNullTransport(logger)` is the boot default when SMTP is unconfigured and reports HONESTLY (`ok: false`) so nothing ever claims an undelivered digest as sent; `createSmtpTransport()` (`smtp-transport.mjs`) is the production transport over nodemailer ^10.2.1 — the ONLY module that imports it, loaded lazily (dynamic import) solely when `SMTP_HOST` is set, so the unconfigured default path never even parses the dependency. No CC/BCC in the interface by design: one explicit recipient per send.
- **Scheduler — opt-in, honest about latency vs duplication:** `startWeeklyDigestScheduler` (wired in `server.mjs` beside the #62 retention sweep, unref'd timer) runs one pass at boot (downtime catch-up — a server that was down over the Monday boundary still sends) then every `WEEKLY_DIGEST_INTERVAL_MS` (default 1h; `0` disables scheduling). Extra ticks are no-ops by the sent-ledger, so the interval bounds worst-case SEND LATENCY, never duplication. `WEEKLY_DIGEST_ENABLED` (accepts `1`/`true`/`yes`) defaults OFF — outbound mail is a side-effecting surface and a bare dev boot never sends anything; enabling it without `SMTP_HOST` REFUSES TO START with a loud error (an operator who enabled mail meant to send mail — no silent null-transport forever).
- **Env vars:** `WEEKLY_DIGEST_ENABLED` (default off), `WEEKLY_DIGEST_INTERVAL_MS` (default 3600000), `SMTP_HOST` (the one required knob — its presence selects the SMTP transport), `SMTP_PORT` (587), `SMTP_SECURE` (`true`/`1` for implicit TLS 465; otherwise STARTTLS), `SMTP_USER`/`SMTP_PASS` (credentials only ever in env), `SMTP_FROM` (envelope From, default `Balashikshana <no-reply@balashikshana.local>`).
- **Idempotency — claim-on-success, overlap-locked, at-least-once documented:** the `weekly_digest_sent` ledger (migration 012, PK `(parent_id, iso_week)`) is inserted with `ON CONFLICT DO NOTHING` only AFTER a send resolved ok — a failed send leaves no row and is retried by the NEXT run (never mid-run), and a sequential re-run or process restart sends nothing. Concurrent runs are serialized by a session-scoped `pg_try_advisory_lock` (key `0x6d61696c`, a dedicated pooled client held for the run — an overlapping run skips; failure to LOCK proceeds unlocked under the standing single-instance assumption rather than skipping mail). The honest residual window: a process crash between a successful send and its ledger insert loses that one marker row, and the next run may re-send that parent ONCE, then never — bounded to the crash instant, the single point every at-least-once mail system carries.
- **Digest week = the most recently COMPLETE ISO week:** at any instant in week W the digest describes W-1 — partial weeks are never summarized, and the first tick at/after Monday 00:00 UTC sends the week that just closed (within an hour on the default tick). `isoWeekKey` derives the ISO year from the week's THURSDAY (the ISO-8601 rule — Jan 1-3 can belong to the previous ISO year's week 52/53), unit-tested across year seams; the key shape `YYYY-Www` is CHECK-constrained in the ledger.
- **Parity by construction:** every digest number comes from the SAME shared helpers the portal serves — `weeklySeriesForChild` (portal.mjs, which #62's export also reuses) for the week row, the children-overview keys SQL for Silver/Gold counts. One aggregation, three renderings (portal chart, export JSON, email); the digest never forks the math, and deep-equality tests pin digest numbers to `weeklySeriesForChild` output.
- **D5 posture — no links, no images, anti-phishing by omission:** the rendered email (pure renderer, snapshot-tested) contains zero images, zero links, zero beacons or third-party embeds of any kind — asserted by test over the rendered output. No links is deliberate: a link is the one element a phishing copy would abuse, so the footer instead NAMES where to manage preferences ("Manage your email preferences in the parent portal settings") without linking. No tracking pixels or mail analytics exist anywhere in the pipeline.
- **PII minimization:** the email carries each child's nickname and aggregate numbers ONLY (time practiced, topics completed, cumulative mastered, units mastered this week, Silver/Gold keys, streak) — nicknames HTML-escaped in the renderer. Logs are counts and parent-id-keyed outcomes; the recipient address never enters a log line (the #62 doctrine).
- **Gating (each category counted in the run-summary log):** sends go only to parents with a VERIFIED email (`parents.email_verified_at`), the weekly toggle ON (`parents.weekly_email_enabled`, default on), and at least one CLAIMED child (a parent whose last child was deleted via #62 gets no digest). No child recipients, no third-party recipients. Sends are sequential with a small inter-send delay; one parent's failure logs a structured line and the batch continues.
- **Parent controls:** the toggle is parent-level (the digest is one email per parent), exposed at `GET`/`PUT /api/portal/notification-preferences` (parent-token auth, additive in `docs/openapi/baseline.yaml`) and in the portal's Email preferences pane (`apps/parent-portal/src/components/EmailPreferences.tsx`). Flipping it takes effect on the next run — the job reads the flag at selection time.

## 4. Child Safety, Privacy & Compliance (COPPA)

- **Zero Third-Party Behavioral Advertising:** No ad networks or external tracking SDKs in the child-facing app.
- **Parental Gate:** Pin/math verification required before accessing external links, account settings, or subscription management.
- **Verifiable Parental Consent:** every child-data-creating route (student creation, child-profile creation, legacy claim, practice completion, mastery-gate evaluation) is gated server-side on a timestamped consent record naming the current policy version; consent evidence is append-only, and a policy version bump requires re-consent before further child-data creation (see `services/api/consent.mjs` and `docs/database-migrations.md`).
- **Child Profiles & Device Sessions (roadmap D4):** children are profiles owned by a parent account — creation writes the student row, the `parent_children` binding, the devices row, and a student-scoped consent row in one transaction, so no new standalone student can appear. Legacy standalone students (migration 005's status flag) are claimed by exactly one parent — legacy-status-only eligibility, username + PIN proof-of-knowledge, an atomic row-mutex backed by a partial unique index (second claimant rejected) — or archived (removed from the login-screen listing, every session revoked, all student-scoped routes frozen). Child device tokens — the third bearer kind beside student and parent sessions — are minted by an authenticated parent per (child, device), stored hashed at rest, expire after 30 days, and are revoked parent-side with immediate effect (see `services/api/children.mjs` and migration 005).
- **Data Minimization:** Child profiles store only a first-name nickname, grade level, and learning telemetry tied to the parent's authenticated account.
- **Parental Data Rights (roadmap E11, issue #62):** parents can export everything held for a child as one JSON document (data portability; numbers identical to the portal by construction) and delete a child's data through the portal behind password re-authentication + hold-to-confirm, executed as one audited transaction. Consent evidence is retained for COPPA record-keeping with its child linkage severed — the opaque linkage survives only in the append-only `deletion_audit` ledger (see architecture sec 3.5 and migration 011).

## 5. Deployment & Operations (M6, issue #64)

- **Topology:** `infra/` holds validate-only Terraform for AWS — dev/staging/prod provision from byte-identical environment roots over five shared modules (`network`, `postgres` RDS 16, `api_service` ECS Fargate + ALB + TLS, `static_site` S3 + CloudFront for the portal, `packs_store`). Environments differ only by `terraform.tfvars` (test-enforced). Full runbook, provider decision record, and the environment matrix: `docs/deployment.md`.
- **Doctrine:** CI runs `terraform fmt` + `validate` only (pinned 1.5.7, no cloud credentials, no state); `plan`/`apply` are human steps under the standing manual-deploy preference. Secrets live in SSM Parameter Store under `/balashikshana/<env>/*` and are injected into tasks by ARN — never committed (scan- and gitignore-enforced).
- **Migrations on deploy:** a one-off ECS task runs `npm run migrate` (node-pg-migrate) BEFORE the new version takes traffic, gated on exit code; boot-time idempotent migration in `db.mjs` remains the backstop. The post-deploy smoke (`scripts/post-deploy-smoke.mjs`) fails any deploy where health (6,140-question seed), curriculum, practice, the content-pack index, or the portal origin misbehaves.
- **Single-instance decision (roadmap D2, revisited):** the API runs one task per environment by default. The retention sweep and weekly digest hold `pg_try_advisory_lock`, so scheduled work is already second-instance-safe; what is NOT is the per-process rate-limit buckets — Redis (or an equivalent shared store) re-enters the stack exactly when scaling out, not before. The unused compose Redis service was removed in #64 (nothing ever read `REDIS_URL`). Rationale and the multi-instance path: `docs/deployment.md` "Single instance vs multi-instance".
- **Edge slot for the gateway (roadmap D10, issue #65):** `gateway.<env>.<zone>` is reserved via a placeholder record so Dwara can front the public API without a second migration of DNS or runbooks.
