# Technical Architecture (iOS, Android & Cloud Sync)

**Balashikshana** is architected as an **offline-first, cross-platform mobile game and study platform** for **iOS and Android** tablets and phones, backed by a containerized microservice API for multi-device progress synchronization, parent analytics, and over-the-air (OTA) curriculum bundle delivery.

## 2. Mobile Client Architecture (iOS & Android)

### 2.1 Cross-Platform Layer
- **Runtime:** React Native (Expo SDK 58, RN 0.88, React 19 — roadmap D1) with **React Native Skia**, **Reanimated 4**, and **Rive**.
  - **60/120 FPS Rendering:** Skia provides hardware-accelerated 2D canvas drawing for Bezier letter tracing (`trace-draw-studio`), particle effects, ten-frame physics blocks (`block-builder`), and fast-moving sprites (`bubble-pop-blitz`).
  - **Vector Animations:** Rive state machines power interactive characters and study manipulatives at `< 50 KB` per asset.
- **App Shell & Design System (M3, issue #43):** the shipped foundation every M3 screen builds on.
  - `apps/mobile/src/design/tokens.ts` — pure-data single source for color (semantic `light`/`dark`/`highContrast` themes + text-grade `statusInk`), spacing, radius, and the kid-scale type ramp; vitest-enforced invariants (>= 48pt touch targets, WCAG contrast floors per theme).
  - Primitives (`Button`, `PressableCard`, `ProgressBar`, `Badge`, `Sheet`) with the tactile 3D treatment and a global reduced-motion provider (`MotionProvider` honors the OS accessibility setting; zero-duration degradation, nothing load-bearing).
  - `expo-router` tree: launcher + the real onboarding flow (below) + the readiness-guarded real `journey` map (2.7) + placeholder `practice` / `gate` runners (their param contract is already fixed: `{ gradeId, unitId }`); no dead ends.
  - Quality gates: ESLint (flat, `eslint-config-expo`) + Prettier + strict `tsc` + vitest, wired into the single CI job.
- **Onboarding & Consent Chain (M3, issue #44):** the client that drives the M2 parent/consent/child API end to end (`src/onboarding/`).
  - A pure state machine (`state.ts`) with a resume planner: the step snapshot (one-row `expo-sqlite` table, secret-free) plus secure-store credentials plus a read-only server reconcile (consent status + children) decide the landing step after any interruption. Duplicate safety comes from in-flight markers persisted before the create-child POST — a kill mid-submission adopts the landed child or re-submits, never both.
  - Storage seams (`storage.ts` + `nativeStores.ts`): every credential (parent session, child-device, pending verification token, draft child PIN, install device id) routes exclusively through `expo-secure-store`; the SQLite snapshot is structurally incapable of carrying a secret, and the vitest suite enforces that on serialized snapshots.
  - Client consent doctrine: consent is captured before any child-data call, re-asserted server-side before child creation, and a 409 `policy-version-mismatch` always re-renders the new policy text before re-acceptance. A policy bump re-locks child surfaces (the journey guard consults consent status; offline it falls back to the last-known accepted version while the server remains the enforcement authority).
  - Parental gate: a reusable hold-to-confirm component (3-second continuous press, timer-based — animation settings cannot affect it) guarding onboarding and every parent/settings surface.
- **Audio & Phonetics Subsystem (M3 infrastructure, issue #45):**
  - `AudioCoordinator` facade (`apps/mobile/src/audio/`): the single entry point screens consume — `speak()` (TTS narration), `sfx()` (feedback sounds by id or `{moment, topicId}`), `haptic()` (feedback patterns), `stopSpeech()` (synchronous duck restore). Every platform capability is injected (speech / SFX / haptics / bundled-narration engines, settings store, clock, accessibility probes), so the entire policy surface is node-testable; the Expo adapters are isolated in one RN-only module (`nativeAudio.ts`) and the service bootstraps at the root layout via `getAudioService()`.
  - Grade-calibrated narration rate: rates derive from the curriculum registry (`docs/us-curriculum-registry.json`, per-topic `voiceNarration.speakingRateWpm`, uniform per grade — Pre-K 110, K 120, G1 130, G2 140, G3 150) and are clamped to 110–150 WPM before conversion to the platform multiplier. SSML narration input is adapted per platform (expo-speech has no SSML: tags stripped, prosody rates honored, break pauses preserved).
  - Duck policy (`duckPolicy.ts`, pure count-based state machine): while any narration utterance speaks, SFX volume scales to 0.3; the multiplier restores only when every queued utterance reaches a terminal event (paired with its start), and cancel restores synchronously. Narration itself is never attenuated — it is the primary instructional channel for pre-readers — and narration defers while a screen reader is active so TTS never fights VoiceOver.
  - Manifest-driven SFX catalog: `assets/sounds/sounds-manifest.json` (repo root, 614 topics) references the 16 synthesized WAVs in `assets/sounds/`; the app's static asset registry is compile-time pinned to exactly those 16 stems and tests pin manifest == registry == disk in both directions. #46 (content packs) owns the on-device split and delivery of topic-to-soundpack data; until then the bundled manifest is the source.
  - Audio settings (sound effects / narration / haptics / music toggles) persist through the non-secret SQLite seam (`balashikshana_audio.db`, one-row, schema-version-guarded parse with per-field type guards) — never the secure store.
  - Pre-K fallback hook: when the device exposes no usable TTS voice, a bundled-narration seam is attempted before reporting `unsupported` (bundled audio coverage itself lands with #59).
  - Pre-packaged pure phoneme audio bank (`/m/`, `/s/`, `/a/`, `/sh/`, `/ch/`) for zero-latency phonics blending (planned with the bundled-audio milestone).
  - On-device Text-to-Speech (US English voice profile) for dynamic math word problem narration so pre-readers are tested on math reasoning rather than reading ability.

### 2.2 Procedural Question & Distractor Generator
Instead of static multiple-choice questions that children memorize after two attempts, each Skill Topic in [`us-curriculum-registry.json`](./us-curriculum-registry.json) is paired with a **Parameterized Question Generator**:
- Generates fresh numbers, visual configurations, and pedagogical distractors on every run.
- **Smart Distractor Generation:** Wrong choices are generated from common misconception models (e.g., for `52 - 18`, distractors include `46` [subtracted smaller from larger digit: `8 - 2`], `44` [forgot to borrow], and `36` [off-by-two computation error]).

### 2.3 Local-First Storage & Offline Play
- **On-Device SQLite Database:**
  - `learner_profiles`: Child UUID, avatar, current grade, motor baseline ($T_{\text{motor}}$).
  - `unit_progress`: `unit_id`, `status` (`LOCKED`, `STUDY_REQUIRED`, `GUIDED_PRACTICE`, `FLUENCY_READY`, `GATE_UNLOCKED`, `MASTERED`), `best_accuracy`, `best_median_speed_ms`, `attempts_count`.
  - `topic_mastery`: `unit_id`, `skill_topic_code`, `mastery_score` (0–100), `median_speed_ms`, `stability_days` ($S_m$), `last_reviewed_at`, `cpa_fading_stage`.
  - `assessment_telemetry`: Granular log of every gate attempt (`question_id`, `skill_topic_code`, `is_correct`, `raw_time_ms`, `cognitive_time_ms`, `fluency_grade_1_to_4`).
  - `spaced_repetition_queue`: `unit_id`, `skill_topic_code`, `retrievability_pct` ($R_m(t)$), `next_review_at`, `sleep_consolidation_key_state` (`SILVER_KEY` / `GOLD_KEY`).

### 2.4 Signed Content Pack Subsystem (M3, issue #46)
- **Compile-time (`tools/content-pipeline`):** the registry is compiled into one deterministic SQLite pack per grade — canonical JSON, fixed pragmas, single sorted transaction, `VACUUM`, no timestamps — then sealed with a detached Ed25519 signature and SHA-256 checksum in a manifest index. The same registry + key always rebuilds byte-identical artifacts, and the build refuses to publish any artifact that fails its own self-verification.
- **Serving:** the API serves the manifest index (`GET /api/content/packs`) and the signed artifacts (`GET /api/content/packs/:gradeId`, octet-stream, ETag = sha256) from the gitignored compiler output; it never verifies signatures (that is the device's job) but 503s on any index/artifact inconsistency.
- **On-device (`apps/mobile/src/content/`):** packs are verified before install — pinned public keys, size + checksum + signature, and a `pack_info` cross-check that the artifact describes exactly the grade/version the manifest promised — then published with one atomic rename and pruned under a 64 MB storage budget. Downgrades are refused; failed installs leave the previous pack active. Pack artifacts are opened read-only (`PRAGMA query_only`); content rows are never inserted on-device.
- **Trust model:** dev builds pin the committed dev key; production pins nothing until the release key is provisioned at M6 — an empty trust list fails closed (no pack installs) rather than trusting the dev key.
- **Forward schemas:** the pack lifecycle database (`balashikshana_content.db`) already carries the append-only `attempt_log` and `topic_progress` / `unit_progress` tables that the offline practice core (#47) and sync protocol (#48) populate.

### 2.5 Offline Practice Core (M3, issue #47)
- **Module layout (`apps/mobile/src/practice/`):** a pure, node-testable core — `PracticeSessionEngine` (topic / boss-gate / Gold-verification session orchestration), `AttemptRecorder` (append-only writes), `progressProjector` (attempts -> progress rows), `goldKey` (two-key state machine), `reviewQueue` (spaced-repetition due queue), `packShapes` (pack rows -> core-engine shapes, field-identical to the server's `mapQuestionRow`) — with exactly one RN adapter (`nativePractice.ts`: expo-sqlite lifecycle storage + a cached, `PRAGMA query_only` pack reader resolved through `pack_meta`) and a root-mounted `PracticeWarmup` fire-and-forget bootstrap. `packages/core-engine` is imported read-only via a `file:` workspace link and never modified (RN-side typings: `apps/mobile/src/types/core-engine.d.ts`); the Hermes export for both platforms is asserted to contain the engine.
- **Local D8 doctrine:** the attempt log is client-authoritative and append-only — INSERT is the only write, there is no UPDATE/DELETE path anywhere in the mobile tree (source-scan enforced), the AUTOINCREMENT `id` is the strictly monotonic sync cursor, and `synced` flips to 1 only after the #48 sync worker has durably applied the server's authoritative snapshot (the one documented UPDATE exception; the source-scan test pins that exact statement shape). Progress rows are a local projection of the log; responses are durable at submit time, projections run at session completion, so a crash mid-session loses no attempt data (the log is the recovery record; the server re-derives on sync).
- **Equivalence contract:** the projector mirrors `services/api`'s topic-complete and gate-evaluate derivations line-for-line — same engine calls, same rounding (`toFixed(1)` accuracy, `toFixed(2)` median), same crowns rule (3/2/1/0 at >= 95% and at-target speed / >= 85% / >= 80%), same GREATEST/LEAST upsert merges, sticky `MASTERED`, key COALESCE (an existing key is never nulled). Tests run identical streams (fixed + seeded-random) through both consumption paths and assert identical projections; a source tripwire pins the server's load-bearing derivation lines so server changes break the proof loudly. #48 resolved the #47 divergence list: (1) both sides now run the registry two-key machine — Silver on pass, Gold only via the frozen 14-hour window plus a 5-item verification with >= 4 correct (`services/api/derivations.mjs` is the single source the online handlers AND the sync reconciler reuse; the pre-#48 any-second-pass Gold promotion is retired); (2) topic-path cognitive time is computed with audio duration 0 exactly like the server's topic handler, while gate items use the engine's audio-aware rule; (3) the server now persists all three session types (migration 006; online rows get per-call session ids, synced rows carry device ids + client sequence numbers). Local gate outcomes and key states carry `provisional = 1` until a sync snapshot confirms or rolls them back.
- **Schema v2 (lifecycle DB):** purely additive `ALTER TABLE ... ADD COLUMN` statements plus the partial `idx_attempt_log_drain (student_id, id) WHERE synced = 0` — v1 statements are frozen, a v1 device upgrades in place with zero data movement, and the `user_version` runner never touches a database from a newer app version. `attempt_log` gains `unit_id`, `session_type` (`TOPIC_PRACTICE` / `GATE` / `GOLD_VERIFICATION`), `session_id`, `raw_time_sec`, `fluency_grade`, `misconception_tags_json`, `chosen_answer`; `topic_progress` gains the SR columns (`stability_days`, `next_review_at`, `last_review_at`, `fluency_grade`, `topic_code`, `provisional`); `unit_progress` gains the gate-projection columns (`best_median_speed_sec`, `stability_days`, `last_reviewed_at`, `cpa_stage`) plus `provisional`, `silver_awarded_at`, `gold_verified_at`.
- **Two-key sleep consolidation (registry `globalMasteryRules.twoKeySleepConsolidationGate`):** day-1 pass -> `SILVER_KEY` (provisional); Gold eligibility opens exactly 14 h after the FIRST Silver award (re-passing the gate never resets or re-arms the window); a 5-item verification with >= 4 correct upgrades to `GOLD_KEY` (provisional); transitions are forward-only — no local event revokes a held key (rollback is #48's server-authoritative concern).
- **Spaced repetition:** the review queue ranks due `topic_progress` rows by the engine's retrievability `R_m(t)` (most-forgotten first), and intervals are age-capped per grade from the pack's `sr_max_interval_days` (Pre-K 21 / K 30 / G1 45 / G2-G3 60 days) — the cap is enforced both inside `updateTopicMemoryStability` (via the per-grade policy) and again at scheduling time.
- **Question sourcing offline:** stored pack rows first (topic sessions: `difficulty ASC, question_id ASC LIMIT n`, mirroring the server's practice endpoint; gate sessions: the server's stratified round-robin across the unit's topics), with the engine's deterministic `generateTopicPracticeSet` padding any shortfall in a disjoint `-G` id space — identical items for identical seeds on both sides by construction.

### 2.6 Sync Protocol (M3, issue #48)
- **The loop (roadmap D8):** the mobile `SyncEngine` (`apps/mobile/src/sync/`) drains whole sessions from `attempt_log` in id order (front window via `idx_attempt_log_drain`, capped at the server's batch limit), uploads ONLY facts (raw time, audio, answers, tags, motor baseline — never client-computed derivations), adopts the server-authoritative snapshot (confirming or rolling back provisional local state, adopting server timestamps), and only then flips `synced`. A crash at any step loses nothing: rows replay, and the server dedupes by `(student, device, client_seq)`.
- **Whole-session contract with boundary deferral:** a batch carries only complete sessions. When the drain window is FULL, a cursor probe (`drainUnsyncedAfter` — rows strictly after the window's last id, never a re-read of the window) decides the trailing session's fate: it uploads whole only if the probe PROVES it ended (the unsynced remainder is exhausted, or a different session follows its last row) AND the extension fits the 200-attempt cap; otherwise the trailing session is DEFERRED and only the complete prefix uploads — the next pass's window starts at the deferred session's head, so a session that fits the cap always uploads whole and progress is guaranteed. A session larger than the cap is a loud fatal, never a silent split. Sessions the child is still answering (liveness probe) defer the same way. Uploadable groups are a strict prefix stopping at the first deferred group, so the synced-flag range flip (`markSyncedUpTo`) can never mark unuploaded rows. A configured batch size above the server cap is clamped client-side to 200 rather than wedging on a fatal 400.
- **Server reconciler (idempotent + convergent):** `POST /api/sync/attempts` (child-device tokens only — student binding and the idempotency device component both come from the token, never the body; consent-gated; archived children frozen out) inserts each attempt with `ON CONFLICT DO NOTHING` on the unique `(student, device, client_seq)` key, then — in the SAME transaction — replays every session that gained rows through the exact shared derivations the online handlers run (`services/api/derivations.mjs`). Defense-in-depth convergence: each replay runs over the UNION of the batch group and any previously persisted rows of the same `(student, session_id, session_type)` (the `idx_attempts_session` lookup), with exactly-once counting (a re-replayed session adds no count) and coin awards gated on the pass transition — so a client that violates the contract and splits a session across batches converges on the true session instead of double-counting it. Gold verification converges by construction (verdict over the union, forward-only transition). Documented residual: spaced-repetition stability takes exactly one growth step per session, at first arrival; a re-replay carries the stored stability and CPA stage through (the growth function is clamped, not invertible). `GET /api/sync/progress` returns the authoritative snapshot plus the content-version handshake without an upload.
- **Clock policy:** server timestamps are authoritative. Client `answered_at` in the past is accepted as-is (offline devices legitimately lag); a future timestamp beyond `SYNC_FUTURE_CLOCK_TOLERANCE_MS` (default 5 minutes) is clamped to server receive time and counted in `stats.clockSkewAdjusted`. The 14-hour Gold window is evaluated at the session's own adopted timestamp, so sync latency never extends eligibility.
- **Server schema (migration 006):** `student_question_attempts` gains `audio_duration_sec`, `session_id`, `device_id`, `client_seq` plus the partial unique index `uq_attempts_client_seq` (replayed batches insert nothing) and `idx_attempts_session` (the union-replay lookup); `student_unit_progress` gains `silver_awarded_at` / `gold_verified_at` (the two-key machine's persisted state). Attempts are immutable COPPA evidence: `device_id` deliberately has no foreign key into `devices()` so deleting a device row never cascades away its history.
- **Transport and battery doctrine:** the engine retries with exponential backoff + full jitter (fatal 400/401/403/404/413 never retry); offline runs pause without touching the transport. The controller fires only on app foregrounding, connectivity regain, and debounced post-practice nudges — no polling loops. Connectivity uses `@react-native-community/netinfo` (the supported reachability API for Expo; Expo SDK 58 ships no first-party connectivity module — decision documented in `nativeSync.ts`). `SyncBootstrap` mounts the controller at the root layout. Since #49 the bootstrap also wires the previously-dormant `clientPacks` handshake — the transport reports the device's active `pack_meta` versions on every upload/progress fetch, the server's `packsOutdated` answer reaches subscribers through `subscribeContentOutdated` (the journey's grade switcher marks stale grades), and the controller singleton is exported (`getSyncController()`) so screens share one in-flight-guarded instance. Endpoints, schemas, and the whole-session/clock contract are specified in `docs/openapi/baseline.yaml` (additive; oasdiff-gated).

### 2.7 Journey Map Screen (M3, issue #49)
- **Module layout (`apps/mobile/src/journey/`):** the same DI doctrine as practice/sync — a pure, node-testable derivation layer (`model.ts` states + garden math + deterministic winding layout, `store.ts` screen state machine, `loader.ts` pack+progress assembly, `art.ts` a11y art contract) with exactly one RN adapter (`nativeJourney.ts`: identity/snapshot, pack currency) plus the RN views (`JourneyScreen`, `JourneyPath`, `GardenHealth`, `GradeSwitcher`). Zero curriculum data in the module — everything renders from the installed #46 pack (query_only reader) and #47 progress rows; a vitest source-scan enforces both that and the no-native-imports purity of the pure layer.
- **State derivation:** all seven engine `UNIT_STATES` are computed, never stored — precedence LOCKED (any unmastered prerequisite, resolved inside the grade) > MASTERED / REMEDIATION_REQUIRED (unit row) > GATE_UNLOCKED (every topic complete at avg crowns >= 2, the projector's 85%-accuracy tier) > FLUENCY_READY (every topic complete) > GUIDED_PRACTICE > STUDY_REQUIRED; a held key is forward-only and outranks the ladder. Keys ride `unit_progress.key_state` with the provisional distinction (sync adoption clears it) and the 14-hour Gold-verification countdown; the FLUENCY_READY / GATE_UNLOCKED split is the journey's documented reading of the engine ladder (matrix-tested at the exact tier boundaries). Garden health is a pure aggregate (per-unit mastery fractions + gate-attempt health) — no hardcoded values.
- **Rendering:** one `react-native-svg` surface carries the track, nodes, glyphs, and key badges (path `d` and node centers precomputed by the deterministic `layoutWindingPath`, memoized on unit count + width only); node touch targets are thin >= 48pt Pressables over the surface. The single animated surface is the scroll-linked dash reveal (reanimated shared value, mounted only when the motion profile allows; reduced motion renders the static reveal). Added dependency: `react-native-svg` 15.16.0 — chosen over Skia (established OSS standard, lighter, sufficient for a static winding path; reanimated already covers motion).
- **Hydration and grade switching:** on mount the screen loads the local model first (offline-first), then kicks ONE sync run through the shared controller (`getSyncController()`) and re-derives with fresh post-snapshot data; the post-adoption reload targets the live grade via a ref. The store's `model-loaded` is guarded by the active grade, so a hydration racer can never render one grade's units under another grade's selection. Grade switching persists through the onboarding snapshot's `gradeId`; per-grade progress is preserved structurally (unit ids are globally unique). The switcher's pack currency — `installed` / `downloading` / `missing` / `stale` — runs missing/stale selections through the #46 `ensurePack` lifecycle (deduplicated per grade, downgrades refused; a stale flag keeps serving the installed last-good pack until the update resolves).
- **Accessibility:** every state encoding is shape+color redundant — a unique SVG glyph per state, Silver badge = circle, Gold = hexagon — and each node's spoken label carries state, key, provisional flag, countdown, topic census, and "you are here". Works unchanged in the `highContrast` theme (theme-independent glyphs; only fills resolve per theme).
- **Navigation seam (#50/#51):** node taps route to `/practice` and `/gate` with `{ gradeId, unitId }`; gate-adjacent states (FLUENCY_READY / GATE_UNLOCKED) go to `/gate`, everything actionable to `/practice`, LOCKED is disabled. The behavior comparison against the dev harness (D1 input) is documented in `docs/journey-harness-parity.md`.

### 2.8 Practice Session Runner (M3, issue #50)
- **Module layout (`apps/mobile/src/runner/`):** the same DI doctrine as practice/sync/journey — pure, node-testable modules (`interactionRegistry.ts` renderer registry + coverage check, `cpaStages.ts` stage ladder, `questionShapes.ts` row-to-widget adapters + render matrix, `requeue.ts` expanding-retrieval scheduler, `sessionStore.ts` UI state reducer) behind a pure-only barrel (`index.ts` exports nothing that transitively imports native modules); the RN layer is exactly the widget kit (`widgets/`, importable directly by the M4 game framework's practice-runner fallback, #52), one native-seams module (`runnerNative.ts`: engine singleton, audio coordinator, child-device identity), the 3-tap `MotorWarmup`, and the thin `PracticeRunnerScreen`. No network call exists in the runner tree — a full session runs offline from the installed #46 pack + the #47 engine.
- **Interaction inventory is data-derived, never hand-listed:** the seeded packs contain exactly three `interaction_type` values (multiple-choice 5,228 / tile-builder 712 / interactive-counter 200 of 6,140 rows), and `tests/runner-interaction-coverage.test.ts` re-derives that inventory the same way the #46 compiler seeds it (engine `generateTopicPracticeSet` over every registry topic), failing when any type has neither a renderer in `interactionRegistry.ts` nor an entry in `TRACKED_FALLBACK_TYPES` (empty at v1). The same test pins `docs/runner-interaction-coverage.md` — the human checklist — to exactly the derived inventory, so code, test, and doc cannot drift.
- **CPA scaffold ladder (engine-owned, mirrored not forked):** `stageForTopicProgress` reproduces the engine's `updateTopicMemoryStability` cpaStage thresholds line-for-line — stabilityDays < 1 `CONCRETE_INTERACTIVE`, >= 1 `PICTORIAL_STATIC`, >= 4 `PICTORIAL_GHOST_FLASH_1S` (a 1-second visual peek, then hidden), >= 10 `PURE_ABSTRACT_SYMBOLIC` — pinned against the engine across a stability sweep by `tests/runner-cpa.test.ts`. The stage ALWAYS comes from engine state (the topic's memory stability in the #47 progress projection), never from UI heuristics; a topic with no progress row starts concrete. `renderPlanFor` composes the interaction-type x stage matrix: the interactive manipulative is the answer surface only at the concrete stage; every later stage fades to the choice grid with progressively less scaffold (static picture -> 1-second flash -> none). Every seeded row carries a non-empty `choices` array (asserted), so the choice grid is the universal degraded-stage surface and no question can ever render unanswerable.
- **In-session expanding-retrieval re-queue:** the pure scheduler (`requeue.ts`) inserts three re-presentations of the SAME question row at Lag +2/+5/+10 intervening items when an ORIGINAL item is graded 1 (missed) or 2 (slow) — the constants are pinned equal to the engine's `intraSessionExpandingLags` by `tests/runner-requeue.test.ts`. A miss on an already re-queued item never extends the ladder (bounded, gentle sessions); a slot past the tail clamps to the tail — the +10 presentation becomes the session's "exit ticket" — and the queue is capped at 16 total items (re-queues past the cap are dropped; the cross-session spaced-repetition schedule still owns the topic). Re-queued presentations carry a SPACED REPLAY badge.
- **Widget kit v1 contracts (`src/runner/widgets/`):** `CounterFrame` (five-column tap-to-toggle counting frame — the manipulative IS the ten-frame), `TileBuilder` (tap-to-place tile bank into answer slots — tap, never fine-motor drag, for ages 3-9), `ChoiceGrid` (universal answer surface; selection is shape+color redundant — tinted fill AND solid border AND a check glyph), and `VisualScaffold` (the pictorial/ghost-flash visual row plus the manipulative-anchor chip derived from the row's `visual_aid` stem). All four are presentational (no session/engine/audio knowledge; the parent owns correctness), theme-aware across all three themes including highContrast, >= 48pt touch targets, animation-free (the ghost-flash window is content timing, not animation; press feedback honors the reduced-motion profile; nothing load-bearing animates). Seeded choice sets are test-pinned at <= 4 options, so the non-virtualized grid stays consciously bounded.
- **Deterministic presentation:** choice order is a Fisher-Yates shuffle seeded by a FNV-1a hash of the question id (xorshift32 stream) — no `Math.random` anywhere in the render path, so the same question presents the same order on every device; the seeded rows store the correct answer first, so presentation must never be unshuffled.
- **Motor warm-up and cognitive-time parity:** every session opens with the 3-tap `MotorWarmup`; tap latencies feed the ENGINE's `computeMotorBaselineSec` (median, clamped 0.15-1.5 s) and the result rides every attempt row so #48's server replay reproduces the math. Topic-practice cognitive time subtracts the motor baseline with audio duration 0 — exactly the server's topic-handler rule (`deriveAttempt`) — while narration is client-side (#45 coordinator) and its measured duration is recorded on the attempt row purely as a sync fact, never billed into topic cognitive time; gate/verification paths keep the engine's audio-aware rule.
- **Session store + stale-session guard:** `sessionStore.ts` is a pure reducer over the phases loading / no-pack / error / picker / warmup / question / feedback / summary; it holds no clock and performs no I/O. Session-scoped actions carry the `sessionId` and stale ones are ignored — the same active-id guard doctrine that fixed the #49 journey grade race, so a late async callback for a session the child already left can never poison the live view.
- **Abandon-on-error sync liveness:** both error paths (submit-response failure and complete-session failure) and the confirmed exit call `practiceEngine.abandonSession(sessionId)` BEFORE surfacing the failure. A session id stranded in the engine's active map would stop #48's upload batching at the first active-session group — wedging that session AND every later one until app restart. Abandon keeps already-recorded attempts durable in the append-only log; no projection is written (integration tests prove the liveness map empties under simulated storage faults).
- **Fresh progress reads + grade unification:** the mount-time progress snapshot is refreshed from storage at EVERY session start and EVERY picker rebuild, so a back-to-back second session never computes a CPA stage from stale rows (one stage too concrete). The refresh is best-effort — on a storage read fault the picker still opens on the previous rows (labels may briefly show stale values; the decision path is unaffected and the next successful read self-heals; known low advisory). The effective grade (`gradeParam ??` the snapshot's active grade) is resolved ONCE at mount and reused for narration AND session starts, so the two can never diverge.
- **Route and guard:** `app/practice/index.tsx` is a consent-guarded child surface (same offline-tolerant readiness guard as the journey); the #49 journey map routes into it with `{ gradeId, unitId }` and an optional `topicCode` deep link that skips the picker. Audio rides the #45 `AudioCoordinator` (per-grade WPM narration of the prompt, replay button, SFX moments incl. streak combos and speed-target beats, haptics suppressed under reduced motion); the gentle-retry tone (no fail states, "Almost! Let's look again.") is the Pre-K-G1 voice mandate.
- **Deferred to the M4 archetype packs (#53/#54):** full SVG manipulative art parity — the widget kit renders the manipulatives interactively today (the counting frame IS the ten-frame) with vector fallbacks; the 12 repo SVG illustrations remain the web harness's concrete-stage anchor, and the art pass that matches them lands with the archetype renderer packs (the #52 game framework ships the pipeline with a stub renderer).

## 4. Child Safety, Privacy & Compliance (COPPA)

- **Zero Third-Party Behavioral Advertising:** No ad networks or external tracking SDKs in the child-facing app.
- **Parental Gate:** Pin/math verification required before accessing external links, account settings, or subscription management.
- **Verifiable Parental Consent:** every child-data-creating route (student creation, child-profile creation, legacy claim, practice completion, mastery-gate evaluation) is gated server-side on a timestamped consent record naming the current policy version; consent evidence is append-only, and a policy version bump requires re-consent before further child-data creation (see `services/api/consent.mjs` and `docs/database-migrations.md`).
- **Child Profiles & Device Sessions (roadmap D4):** children are profiles owned by a parent account — creation writes the student row, the `parent_children` binding, the devices row, and a student-scoped consent row in one transaction, so no new standalone student can appear. Legacy standalone students (migration 005's status flag) are claimed by exactly one parent — legacy-status-only eligibility, username + PIN proof-of-knowledge, an atomic row-mutex backed by a partial unique index (second claimant rejected) — or archived (removed from the login-screen listing, every session revoked, all student-scoped routes frozen). Child device tokens — the third bearer kind beside student and parent sessions — are minted by an authenticated parent per (child, device), stored hashed at rest, expire after 30 days, and are revoked parent-side with immediate effect (see `services/api/children.mjs` and migration 005).
- **Data Minimization:** Child profiles store only a first-name nickname, grade level, and learning telemetry tied to the parent's authenticated account.
