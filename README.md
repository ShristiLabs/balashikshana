# Balashikshana — Mastery-Gated Interactive Learning Games (Pre-K to Grade 3)

**Balashikshana** is a cross-platform mobile learning platform (**iOS & Android**) for children in **Pre-K, Kindergarten, Grade 1, Grade 2, and Grade 3 (Ages 3–9)**.

Aligned with the **United States Curriculum** (**Common Core State Standards for Math & ELA**, **Preschool/Head Start Early Learning Guidelines `MA.1–MA.5`**, **NGSS Science**, and **C3 Social Studies**), Balashikshana organizes all **614 Curriculum Skill Topics** (~3,000 micro-skills) into **130 sequential Units of Closely Related Work**.

Every single Skill Topic includes **9 complete asset categories** (**Sounds**, **Images**, **Videos**, **Interactive Elements**, **Voice Narration**, **Animations**, **Games**, **Quizzes**, and **Assessments**), culminating in a strict **Accuracy + Speed Mastery Gate** and a **Child-Calibrated Scientific Spaced Repetition System**.

```text
1. Study & Explore  ──►  2. Guided Practice  ──►  3. Fluency Zone  ──►  4. Unit Boss Gate
```


### 3. API Authentication & Parental Consent
- Every student-scoped route requires a session token: send `Authorization: Bearer <token>` (401 without/invalid/expired token, 403 when the token belongs to a different student). Bearer tokens come in three kinds — **student sessions** (M1), **child device tokens** (issue #42), and **parent sessions** (issue #40) — resolved per request and checked per route (403 `wrong-token-type` on a kind mismatch)
- Obtain a student or child-device token: `POST /api/auth/login` (username or studentId + 4-digit PIN, always required), account creation via `POST /api/students` (PIN required, no default exists; demo-seed PINs are randomly generated and printed once in the API log — creation is consent-gated and, since #42, also binds the new student to the creating parent via `parent_children`), or a parent minting a child device token (see below)
- Revoke a token: `POST /api/auth/logout` (student sessions only; parent and child-device tokens get the 403 `wrong-token-type` problem — parents use `POST /api/parents/logout`) or the parent-side device-session revoke; student and child-device sessions expire after 30 days
- PINs are stored as salted scrypt hashes (N=16384, r=8, p=1, keylen=64; see `services/api/db.mjs`) — child PINs use the identical shared parameters; legacy unsalted-SHA-256 rows are rehashed transparently on next login
- **Parent accounts** (full contract in [`docs/openapi/baseline.yaml`](./docs/openapi/baseline.yaml), `parents` tag): `POST /api/parents/signup`, `verify-email`, `login`, `refresh`, `logout`, `logout-all`, `password-reset/request`, `password-reset/confirm` — scrypt passwords, hashed-at-rest session tokens (7-day TTL, 30-day refresh window, soft revoke)
- **Child profiles under parents** (`children` tag): `GET`/`POST /api/parent/children` (creation is consent-gated and writes the student row, the `parent_children` binding, a student-scoped consent row, and the `devices` row in one transaction), `POST /api/parent/children/claim` (legacy standalone students only — username + PIN proof-of-knowledge, exactly-once, second claimant `409 already-claimed`), `POST /api/parent/children/:studentId/archive` (excludes the child from the login-screen listing, freezes every student-scoped route, revokes all sessions), `POST /api/parent/children/:studentId/device-sessions` + `DELETE .../device-sessions/:sessionId` (mint/revoke child device tokens — scoped to exactly one student + one device, stored hashed at rest, 30-day expiry, revocation kills access immediately)
- **Dev dataset note:** the seeded demo students and every pre-#42 standalone dev student carry `status='legacy'` (migration 005) — claim-eligible via the claim route (username + PIN) or deliberately left unclaimed; nothing is auto-adopted. Archived students disappear from `GET /api/students` and cannot log in or mint sessions
- **Verifiable parental consent (COPPA gate):** `POST /api/students`, `POST /api/parent/children`, `POST /api/parent/children/claim`, `POST /api/practice/topic/complete`, and `POST /api/gate/evaluate` write no child data without a matching consent record — the response is `403 consent-required` (RFC 9457 problem+json carrying the current `currentPolicyVersion`) and nothing is written. Consent rows are append-only and server-timestamped; the capture method (`signup-form` or `re-consent`) is derived server-side, never asserted by the client
- Consent routes (full contract in [`docs/openapi/baseline.yaml`](./docs/openapi/baseline.yaml), `consent` tag): `GET /api/consent/policy/latest` (public — the active policy text to render before onboarding), `POST /api/consent/records` (parent bearer + verified email; records acceptance of `policyVersion`, any version other than the active one is `409 policy-version-mismatch`), `GET /api/consent/status` (parent bearer; `consentCurrent: false` after a policy bump means the parent must re-consent before further child-data creation)
- Run the auth/session security tests: `npm run test:api`

Every request is logged as one structured JSON line (pino) with `requestId`, method, route, status, duration, and client IP; the request ID is echoed back in the `X-Request-Id` response header for support correlation.

The API runs on Fastify v5 with per-route JSON-schema validation. Every error response is an RFC 9457 `application/problem+json` document (`type`, `title`, `status`, `detail`, `instance`; validation failures add an `errors[]` array, 429 adds `Retry-After`). The full route contract is [`docs/openapi/baseline.yaml`](./docs/openapi/baseline.yaml) (OpenAPI 3.1); CI enforces it additive-only via an oasdiff breaking-change gate on every pull request.

### 7. Content Packs — Signed Per-Grade Content Pipeline (`tools/content-pipeline`)
- **Compiler:** the `@balashikshana/content-pipeline` workspace (zero runtime deps: `node:sqlite` + `node:crypto`) compiles `docs/us-curriculum-registry.json` into one deterministic, Ed25519-signed SQLite pack per grade — `pack-<gradeId>-v<contentVersion>.sqlite`. Determinism comes from canonical sorted-key JSON, fixed SQLite pragmas, one write transaction with pre-sorted inserts, `VACUUM`, and no timestamps; the tests build twice (including across separate CLI processes) and compare bytes. Questions come from the same core-engine generator the API seed uses (130 units / 614 topics / 6,140 questions total), so pack content and the served PostgreSQL content agree by construction; `packages/core-engine` itself is imported read-only and never modified.
- **Scripts (repo root):** `npm run packs:keys` generates an Ed25519 keypair (the private `.key` is gitignored and chmod 600; only the `.pub.hex` is committed), `npm run packs:build` compiles + signs + fail-closed self-verifies + publishes to `services/api/content-packs/` (gitignored compiler output), and `npm run test:packs` runs the 20-test compiler gate (determinism, completeness vs registry counts, tamper rejection, node:crypto <-> @noble/ed25519 interop).
- **Serving:** `GET /api/content/packs` (manifest index: version, size, SHA-256, detached signature, key id, counts) and `GET /api/content/packs/:gradeId` (artifact bytes, `application/octet-stream`, `ETag` = the manifest sha256). The server never verifies signatures — verification is the device's fail-closed job; the server only refuses its own inconsistency, answering `503 problem+json` when the index is missing or references a missing / size-drifted / invalidly-named artifact.
- **On-device lifecycle (`apps/mobile/src/content/`):** download to staging → size + native SHA-256 + Ed25519 signature verification against pinned public keys → `pack_info` cross-check (the pack's own grade/version/counts must match the manifest, defeating a validly-signed wrong-content substitution) → storage-budget decision → one atomic rename into place → prune superseded content. Downgrades are refused, a failed or interrupted install leaves the previous pack active, and every step is fail-closed. The lifecycle database (`balashikshana_content.db`, `PRAGMA user_version` migrations) also creates the append-only attempt log and topic/unit progress schemas that #47 (offline practice core) populates.
- **Trust model:** development builds pin the committed `dev-local` public key; **production trusts no keys yet** — the release key is provisioned with the M6 store submission, so until then a production build refuses to install any pack (fail closed: an empty trust list never falls back to the dev key, since anyone can regenerate the dev keypair).
- **Measured sizes (registry v1.0.0):** 0.86–2.33 MB per grade, 9.07 MB for all five grades, against a 64 MB on-device storage budget — over 27x headroom for the largest pack. Packs carry zero media bytes: SVG/audio/video assets resolve by path reference through the bundled repo manifests, and the 16 feedback WAVs ship with the app binary.

### 8. Offline Practice Core (`apps/mobile/src/practice`, issue #47)
The engine is now in the app: `apps/mobile` consumes `@balashikshana/core-engine` as a `file:` workspace link (`packages/core-engine` itself stays zero-dependency and unmodified — the RN-side types live in `apps/mobile/src/types/core-engine.d.ts`), and the dual-platform Hermes export is asserted to contain the engine in both bundles. Everything runs offline against an installed #46 pack; there is no network code in `src/practice/`.

- **Append-only attempt log:** every answered item is INSERT-ed into `attempt_log` (lifecycle DB, schema v2 — additive `ALTER`s via `PRAGMA user_version`) the moment it is answered, with raw/cognitive time, audio duration, fluency grade 1–4, topic/unit ids, session id, motor baseline, and client timestamp. There is no UPDATE or DELETE path on `attempt_log` anywhere in the mobile tree (enforced by a source-scan test); the AUTOINCREMENT `id` is the strictly monotonic **sync cursor**, and the `synced` flag flips to 1 only after the #48 sync worker durably applies the server's authoritative snapshot (the one documented UPDATE exception; partial index `idx_attempt_log_drain` serves both the ordered drain and the beyond-window probe).
- **Local progress projection == server derivation:** topic/unit progress rows are computed by the SAME core-engine calls with the SAME rounding, crowns rule (3/2/1/0 at 95%+speed / 85% / 80%), GREATEST/LEAST merge semantics, sticky `MASTERED`, and key-COALESCE behavior as `services/api`'s `POST /api/practice/topic/complete` and `POST /api/gate/evaluate` — proven by tests that run identical attempt streams (fixed + seeded-random) through both paths and by a tripwire that pins the server's own derivation lines (`services/api/derivations.mjs`, the single source the online handlers and the sync reconciler both reuse). The #47 server-side divergence is resolved by #48: both sides now run the registry two-key machine — Silver on pass, Gold only via the frozen 14-hour window plus a 5-item verification with >= 4 correct (the server's pre-#48 any-second-pass Gold promotion is retired); topic-path cognitive time uses audio 0 exactly like the server; gate attempts are logged locally and, since migration 006, persisted server-side with session identity. All local gate outcomes and key states carry a `provisional` flag until a sync snapshot confirms or rolls them back.
- **Two-key sleep consolidation:** Day-1 gate pass awards `SILVER_KEY` (provisional); Gold becomes eligible exactly `silver_awarded_at + 14 h` and requires the verification session; transitions are forward-only (Silver -> Gold, never regress locally); the window is measured from the FIRST Silver award and never re-armed by re-passes.
- **Spaced repetition:** review queues are built from the engine's retrievability curve over the local `topic_progress` rows, with intervals age-capped per grade from the pack's `sr_max_interval_days` (Pre-K 21 / K 30 / G1 45 / G2–G3 60 days).
- **Module layout (DI doctrine):** pure node-testable core — `PracticeSessionEngine` (session orchestration), `AttemptRecorder`, `progressProjector`, `goldKey`, `reviewQueue`, `packShapes` (pack rows -> engine shapes, field-identical to the server's `mapQuestionRow`) — plus exactly one RN adapter (`nativePractice.ts`, expo-sqlite + query_only pack reader) and a root-mounted `PracticeWarmup` bootstrap that pre-opens the reader at launch. Tests: 133 tests across the ten `apps/mobile/tests/practice-*.test.ts` suites run in plain vitest (node:sqlite), including the airplane-mode end-to-end: full topic session, boss gate, and Gold verification against an installed pack fixture with zero network.

### 9. Sync Protocol (`apps/mobile/src/sync` + `services/api/sync.mjs`, issue #48)
Offline progress reaches the server as immutable facts; the server is authoritative for all derived state (roadmap D8).

- **Client loop:** drain whole sessions from `attempt_log` in id order -> upload facts only (never client-computed derivations) -> adopt the server's authoritative snapshot (confirm/rollback of provisional key states, server timestamps) -> flip `synced`. A crash at ANY step loses nothing — rows replay and the server dedupes by `(student, device, client_seq)`. Retries use exponential backoff with full jitter; fatal 400/401/403/404/413 never retry; offline runs pause the loop. - **Whole-session contract:** batches carry only complete sessions. Full boundary-deferral and convergence semantics: `docs/architecture.md` section 2.6.
- **Server endpoints (child-device tokens only, consent-gated):** `POST /api/sync/attempts` — idempotent batch reconciliation in ONE transaction (inserts + session replays through the shared derivations), returning reconciliation stats and the authoritative snapshot; sessions split across batches converge (union replay over previously persisted rows, exactly-once counting, transition-gated coin awards). `GET /api/sync/progress` — the snapshot plus the content-version handshake without an upload. - **The moments, all spoken through the coordinator:** practice sessions open with the topic's registry intro line; a hint button speaks the registry hint line and lights the mascot's hint glow (the #58 `hint-shown` producer's first live dispatcher); wrong answers speak the registry remediation line; gate ceremonies, completion summaries, and the #56 hearts reframe speak from their copy modules — no hardcoded spoken strings anywhere (test-pinned). The motor warm-up stays deliberately un-narrated: its tap latencies calibrate the engine's motor baseline, and speech would contaminate it.
- **Adaptation, fallback, a11y:** SSML adaptation maps prosody pitch (clamped to the platform's [0.5, 2.0] band) alongside rate and break pauses, with deterministic degradation for unsupported values; a missing line is a warned silent skip — never a crash; the Pre-K bundled-audio fallback seam is exercised for all five line kinds in tests (no audio files ship — narration is synthesized; per-grade content packs already carry the narration slice). Narration defers while a screen reader is active so TTS never fights VoiceOver.
- Architecture detail: `docs/architecture.md` section 2.15.

### 21. Placement Diagnostic (issue #60)
Roadmap E10 (the placement half), the M4 capstone: a short adaptive exploration on first grade entry that finds the child's starting point and grants provisional credit within hard guardrails — a placement never awards keys and never completes anything.

- **Adaptive staircase, seeded deterministic:** each subject strand is probed from unit 1 — correct answers go deeper, a wrong answer gets one confirm item on the same unit (a second wrong sets the frontier; a correct confirm forgives the slip). Confirm items resolve first, strands round-robin, and the whole path is driven by a seeded PRNG in the zero-dependency engine module (`packages/core-engine/src/placement.mjs`) — the same seed walks the same item sequence on every device, and the derived outcome depends only on the recorded answers, never on selection order. Sessions stop when every strand has a confirmed frontier or the 14-item hard cap hits.
- **Kid-optimistic slip forgiveness, bounded:** a once-wrong unit is still credited even if its confirm item is cut off by the item cap — one-tap errors must not pin a young child at the start of a grade they know. The blast radius is bounded by the 4-unit skip-ahead cap (tested exactly at the boundary, applied to both the credited prefix and the recommended start), and the credit itself is provisional FSRS stability (1–4 days) that decays through ordinary spaced repetition if unused — a forgiving run cannot lock in a wrong placement.
- **Server recomputes, never trusts:** there is no submit endpoint. The client uploads `PLACEMENT` attempts through the #48 sync wire, and the server replays the same stream through the same engine module — identical stream, identical recommendation (pinned by agreement tests, including split-batch convergence). Migration 009 stores one authoritative record per (child, grade), overwrite-in-place; per-attempt XP rides the #55 ledger, with no outcome rewards. Placement never awards Silver/Gold keys — only a #51 Boss Gate does — and never starts a child inside a unit whose prerequisites are uncredited.
- **The family decides, gently:** the offer appears once per grade (never blocks the journey map; a kill mid-probe simply re-offers — #44 resumability), and the recommendation screen always shows both "start where recommended" and an explicit "start from the beginning" option. Copy frames it as a short exploration, never a test.
- Architecture detail: `docs/architecture.md` section 2.16.

### 22. Parent Portal Web App (`apps/parent-portal`, issue #61)
M5 (roadmap D4/D5): a separate lightweight **Vite + React 19 + TypeScript SPA** for parents — login with the #40 parent account, children overview, per-child analytics, and the parental controls the SERVER enforces. Deliberately never linked from any child surface (D5 isolation; own origin, dev port 4300).

- **Right-sized stack, zero third-party SDKs:** an SPA (not Next.js) because every screen sits behind login — no SSR/SEO surface, static build only; own lockfile (the `apps/mobile` precedent); hand-rolled components over design tokens; hand-rolled SVG charts (the quadrant is positioned dots, the weekly view bars) so the bundle carries no chart library (COPPA: first-party code only, audited).
- **Parent-token-only API:** every `/api/portal/*` route requires a parent session token — student PIN and child-device tokens are 403 wrong-token-type, anonymous 401. Child ids resolve only through the caller's `parent_children` binding; another parent's child returns the same 404 as an unknown id. SPA keeps the token in-memory + sessionStorage mirror (never localStorage; no cookie surface), one refresh attempt on 401.
- **What the parent sees:** children overview cards (nickname, avatar, grade, streak, mastered units, Silver/Gold keys); the accuracy-vs-speed quadrant per child — per skill topic, accuracy % (split at the 80% pass line) against MEDIAN cognitive speed (split at the unit's own target speed — "fast" means at/under the fluency bar crowns use); weekly active time + progress in Monday-anchored ISO weeks (UTC), zero-filled quiet weeks.
- **Controls enforced server-side, one source of truth** (`services/api/enforcement.mjs`, shared by portal + sync + question-serving): daily time limits (UTC day; once recorded active time is at/over the cap, `POST /api/sync/attempts` refuses today-dated batches with 429 + `Retry-After`, backfill always lands, the crossing session landed in full — D8 append-only); subject/grade content controls (a gated subject serves ZERO questions; the pack index filters by ceiling, above-ceiling artifacts 403 for child callers); fail-closed grade vocabulary (unknown ceiling restricts, unknown unit grade is above-ceiling). Controls gate what is served — they never rewrite recorded attempts, and subject controls cannot be carved out of signed packs (question-serving enforces them instead).
- **Settings home:** migration 010 `portal_child_settings` (one row per claiming parent + child; absent row = platform defaults). Notification settings are the #57 reminder MIRROR — parent-owned defaults, default OFF; the reminder itself stays device-local per D5, delivered to devices as the advisory `parentSettings` block on `GET /api/sync/progress`.
- **Data & privacy pane (issue #62, COPPA data rights):** a per-child card with "Download my child's data" (one JSON document covering every child-data class — profile, attempts, progress, sessions, gamification, placement, consent records, settings — with an analytics block computed through the same aggregation path as the portal charts, so the export's numbers equal the portal's) and "Delete my child's data" behind TWO gates: the account password (server-side re-authentication; wrong password 401, nothing deleted) and a 3-second press-and-hold button (keyboard-equivalent; every interrupted gesture cancels). ### 23. Weekly Parent Email Summaries (issue #63)
The M5 email surface: one idempotent weekly email per eligible parent summarizing each linked child's completed week (time practiced, topics completed, units mastered, Silver/Gold keys, streak) — parent-facing only, off by default, zero third-party mail services.

- **Mailer seam, no provider lock-in:** `services/api/mailer.mjs` defines one transport interface with three implementations — capture (dev/tests, zero network I/O), null (the honest no-config default: drops mail reporting `ok:false`, so nothing is ever recorded as sent that was not), and SMTP (production; nodemailer is imported ONLY inside `smtp-transport.mjs` and only when `SMTP_HOST` is set). Transports resolve a uniform result and never throw — one parent's failed send never aborts the batch; it is retried on the next run.
- **Opt-in scheduler, idempotent by ledger:** `WEEKLY_DIGEST_ENABLED` defaults OFF; when on, one boot pass then a tick every `WEEKLY_DIGEST_INTERVAL_MS` (default 1h — the tick bounds send latency, never duplication). The `weekly_digest_sent` ledger (migration 012, PK `(parent_id, iso_week)`) claims a week only AFTER a successful send, so re-runs and restarts send no duplicates while failed sends retry naturally; overlapping runs skip via a Postgres advisory lock. The one documented residual: a crash between send and ledger insert may re-send that parent once, then never (at-least-once).
- **Same math as the portal, by construction:** the digest reuses the portal's shared weekly aggregation (`weeklySeriesForChild`) and keys queries — digest numbers equal portal numbers equal export numbers, pinned by deep-equality tests. The digested week is the most recently COMPLETE ISO week (Monday-anchored UTC); partial weeks are never summarized.
- **COPPA/D5 posture:** recipients are verified parent emails only — no child recipients, no CC/BCC, one parent address per send; eligibility requires a verified email, the weekly toggle ON (default on), and at least one claimed child. Content is each child's nickname plus aggregate numbers only; the email contains NO links, NO images, and no tracking pixels or third-party embeds of any kind (test-asserted) — the footer names the portal settings instead of linking (anti-phishing by omission).
- **Parent control:** the weekly toggle lives in the portal's Email preferences pane (`GET`/`PUT /api/portal/notification-preferences`, parent-token auth); flipping it takes effect on the next run.
- Architecture detail: `docs/architecture.md` section 3.6.


### 24. Deployment: Terraform IaC, Environments & Deploy Runbook (issue #64)
The M6 deployment foundation: infrastructure-as-code for dev/staging/prod, secrets management, migrations-on-deploy, and a post-deploy smoke gate — delivered as reviewable, validated code. **Nothing provisions automatically**: CI only runs `terraform fmt` + `validate` (pinned Terraform 1.5.7, no cloud credentials); `terraform plan` and `apply` are human steps under the standing manual-deploy preference.

- **Provider & layout:** AWS, single region, minimal parameterized surface — `infra/modules/` (network, RDS PostgreSQL 16, ECS Fargate API service + ALB + TLS, S3 + CloudFront portal hosting, S3 content-pack store) with `infra/environments/{dev,staging,prod}` roots that are byte-identical except `terraform.tfvars` (test-enforced DRY). A `gateway.<env>` DNS slot is reserved for the Dwara edge (#65, roadmap D10). Decision record and alternatives considered: `docs/deployment.md`.
- **Secrets:** SSM Parameter Store `/balashikshana/<env>/*` (SecureString) — `db_master_password`, `smtp_user`, `smtp_pass` pre-created by the operator, `database_url` composed by Terraform; the ECS task injects them by ARN at start. No secrets in the repo, enforced by TWO layers: `.gitignore` (`*.auto.tfvars`, state files) and the `infra-secrets` vitest scan that fails CI on secret-shaped literals.
- **Deploy sequence:** `infra/scripts/deploy.sh <env>` runs the runbook as one command — (1) one-off ECS migrations task (`npm run migrate`, refuses to continue on non-zero exit) BEFORE traffic shifts, (2) rolling replacement behind the ALB health check with connection drain, (3) stability wait, (4) `scripts/post-deploy-smoke.mjs` (health with the 6,140-question seed check, curriculum summary, practice fetch, content-pack index, portal origin — any failure fails the deploy).
- **Redis/multi-instance (roadmap D2 revisited):** single API task per environment stays the default; the schedulers are already advisory-locked, so a second instance is safe for them — Redis re-enters exactly when rate-limit buckets need a shared store. The compose Redis service (never read by any code) was removed; `docker/docker-compose.yml` still runs postgres + api + web for local dev.
- Runbook (bootstrap, secrets, rollback/drain, portal + packs deploys, cost posture): `docs/deployment.md`; module map: `infra/README.md`; architecture: `docs/architecture.md` section 5.

### 25. Dwara Gateway Fronting: Consumers, Edge Rate Limits, TLS Termination, mTLS Admin (issue #65)
The M6 edge layer (roadmap D10): the in-house Dwara Rust API gateway fronts the public API — **the Fastify origin keeps its own auth** (dual-token doctrine, CORS, IDOR-safe middleware unchanged); the edge ADDS per-class consumer credentials, coarse volumetric rate limits layered above the origin's semantic buckets, TLS termination, and an mTLS-only admin surface.

- **Config in-repo:** `deploy/dwara/envs/{dev,staging,prod}.yaml` — staging/prod byte-identical, dev differs only by the loopback origin triple (test-enforced DRY). Validated against the vendored Dwara JSON Schema (provenance-pinned by sha256) by a 62-gate vitest suite in the existing CI test step: schema validity, distinct ref-only credentials (SSM `${...}` references, never literals), admin mTLS isolation (client CA required, admin port never a listener port, no client certs on public listeners), full OpenAPI route coverage, policy registry consistency, D10 `X-Consumer-*` stripping toward the origin, TLS posture, staged-rollout pin, secret scan.
- **Consumers (ADR in `docs/gateway.md`):** `parent-app`, `child-device`, `portal` — API-key CLASS identifiers (public-by-design for the SPA; the origin's session/device tokens remain the only auth), each with daily quotas; admin access is a client certificate on the separate mTLS admin listener. Routes stay `auth_required: false` in stage 1 (deployed clients do not send edge keys yet) — the flip is a deliberate, test-pinned stage-2 change.
- **Rate-limit layering:** edge = coarse volumetric per class/per IP (stacked GCRA, 429 + Retry-After); origin = tight semantic caps (login/signup/reset per IP, sync 30/min per device token). `TRUST_PROXY_CIDRS` (default off) restores true-client-IP keying at the origin behind the edge with peer-checked XFF semantics.
- **IaC:** `infra/modules/gateway` — NLB TCP passthrough (TLS terminates at Dwara, not the LB), ECS Fargate gateway service, the #64 `gateway.<env>.<zone>` edge slot now real, SSM ARN secret injection (keys + TLS material), admin port SG-restricted to internal ops CIDRs (module validation rejects `0.0.0.0/0`). Validate-only as always: CI runs fmt/validate, apply stays human.
- **Verification:** `deploy/dwara/verify-edge.sh` scripts the issue ACs (edge health, key-but-no-session still 401 from the origin, synthetic burst -> 429 with Retry-After, admin rejected without a client cert); `scripts/post-deploy-smoke.mjs --edge-url ...` adds an optional edge path check. Full runbook: `docs/gateway.md`.


### 26. Observability: First-Party Metrics, Alerting, Error Tracking (issue #66)
The M6 telemetry layer (roadmap D5: first-party only — no third-party analytics/error SDK ever): a **zero-dependency metrics registry** (hand-rolled counters/gauges/histograms + Prometheus text exposition, ~1 file instead of the OTel SDK tree) with **bounded label cardinality by construction** — route classes ARE the Fastify route inventory (never raw URLs), enums for methods/outcomes, validator + hard-cap rejection counted on `metrics_observations_rejected_total` — served on a **separate internal listener** (`METRICS_PORT`, loopback by default, optional bearer token, SG-restricted in TF, never public/child-facing, never edge-routed).

- **Correlation:** inbound `X-Request-Id` honored when strictly UUID (else fresh), echoed on every reply header AND in the problem+json envelope (`requestId` extension member — additive OpenAPI change per D11); survives client -> edge -> origin.
- **Dashboards:** `deploy/observability/dashboards/api-overview.json` (Grafana OSS schema, committed, panel exprs cross-checked against exported metrics in CI). Full runbook — SLOs, alert first-response, operator Prometheus/Grafana/Alertmanager wiring, redaction policy, ADRs: `docs/observability.md`.
